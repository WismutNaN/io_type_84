# Архитектура IO Type 84

Статус: проект решения, 2026-09-13. Стек, Windows + USB, открытый проект и возможность добавления других ОС подтверждены пользователем. Подтверждён native HID-протокол, названный здесь `io_vision_v0`, а не SparkLink; см. [исследование](DEVICE_RESEARCH.md).

## Препроект

**Тип:** новое настольное приложение. **Пользователь:** сначала владелец устройства, затем возможно другие владельцы. **Суть:** гибко настраивать клавиатуру, видеть результат на её схеме и расширять поведение действиями компьютера.

**Сценарии:** подключить устройство и прочитать его состояние; выбрать клавиши и изменить назначения/ход/цвета; сохранить профиль и применить его; задать правило по нажатию, последовательности, глубине или контексту приложения; вызвать действие ОС или расширение.

**Допущения:** офлайн для базовой настройки, один активный экземпляр помощника, работа без прав администратора для конфигуратора. **Открытые вопросы:** приоритет первых действий помощника, будущая очередность других ОС и лицензия собственного кода. Неизвестные возможности устройства не становятся требованиями к прошивке автоматически.

## Системный контекст

```text
Пользователь
    |
    v

    | типизированные команды / события и снимки
    v
Tauri 2: IPC, окна, tray, жизненный цикл
    |
    v
Прикладные сценарии Rust ─────────── Хранилище профилей / recovery
    |
    +── Устройство и аппаратная конфигурация ── HID-сеанс ── IO Type 84
    +── Подсветка ──────────────────────────────┘                 |
    +── Правила ← цифровые события Windows / аналоговые данные*  |
    |       |
    |       +── Действия ОС / изолированный исполнитель расширений*
    |
    +── Диагностика: журнал операций, capabilities, симулятор

Обычный ввод клавиатуры ────────────── Windows ── приложения
```

Приложение использует уже работающий HID-драйвер Windows. Собственный kernel/filter driver не нужен для подтверждённого конфигурирования. Возможное глобальное подавление отдельных клавиатур — отдельная сложная задача, не скрытая часть базового транспорта.

<a id="components"></a>
## Компоненты и контексты DDD

Модульный монолит с портами и адаптерами. Контексты имеют собственные модели; обмен между ними происходит через команды, события и типизированные результаты. Микросервисы, локальный HTTP-сервер, event sourcing и отдельная БД на контекст не требуются.

| Контекст/компонент | Ответственность и модели | Публичная граница |
|---|---|---|
| [Device Management](../modules/device.md) | DeviceIdentity, DeviceSession, CapabilitySet, DeviceLayout | discover, connect, disconnect, inspect_capabilities |
| [Device Configuration](../modules/configuration.md) | KeyboardConfiguration, FirmwareLayer, Binding, Actuation, FirmwareMacro, AdvancedBehavior | validate_configuration, plan_device_change |
| [Lighting](../modules/lighting.md) | LightingScene, KeySelection, Gradient, AnimationTimeline, OutputTarget | render_scene, compile_device_lighting |
| [Automation](../modules/automation.md) | RuleSet, Rule, Trigger, Condition, ActionRef, SoftwareLayer | compile_rules, process_event, cancel_session |
| [Actions](../modules/actions.md) | ActionDefinition, PermissionGrant, Invocation, ExtensionManifest | list_actions, invoke, cancel |
| [Application](../modules/application.md) | WorkspaceProfile, DeviceSnapshot, Draft, ChangePlan, ApplyOperation | read_snapshot, edit_draft, validate, apply, recover |
| [Infrastructure](../modules/adapters.md) | HID, Windows input/actions, JSON storage, monotonic clock | Реализации портов |
| Tauri / Vue | DTO, IPC, редакторы и представление состояния | Команды и подписки; без raw HID и shell API |

### Границы агрегатов

- `KeyboardConfiguration` — состояние аппаратных назначений и связанных параметров одной конфигурации. Обеспечивает согласованность ссылок на аппаратные макросы/DKS, допустимость параметров и сохранение неизвестных записей. Это логическая согласованность черновика, не транзакция прошивки.
- `LightingScene` — самостоятельный редактируемый объект. Может компилироваться в статические цвета устройства или исполняться программно; это разные результаты компиляции.
- `RuleSet` — согласованная версия правил и программных слоёв. Активная версия меняется целиком на границе обработки события; редактируемый черновик не исполняется.
- `WorkspaceProfile` связывает версии конфигурации, сцены и RuleSet. Его применение — прикладная последовательность операций с частичным успехом, не распределённая транзакция.
- `DeviceSession` — короткоживущая модель подключения. HID handle живёт только в адаптере, а не в доменном объекте.

### Общий язык и типы

`PhysicalKeyId` обозначает клавишу на схеме, `DeviceSlot` — адрес настройки, `LedAddress` — адрес света, `HidUsage` — код стандартного ввода. Между ними существуют явные отображения. Не использовать один числовой индекс для всех четырёх понятий.

`TravelUm` — глубина хода в целых микрометрах; `DurationMs` — интервалы правил; `EventTimestamp` — монотонное время. Усилие не вводится как измеряемая величина без данных датчика. `FirmwareLayer` и `SoftwareLayer` — разные сущности. Действия аппаратного макроса и действия компьютера имеют разные каталоги и ограничения.

`LightingSurface` разделяет `KeyBacklight` и `LedPanel`. Каждая имеет свою геометрию, адреса и capabilities; 128 RGB-слотов клавиш не определяют устройство панели. Требование и неизвестное — в [LED_PANEL](LED_PANEL.md).

<a id="capabilities"></a>
## Модель возможностей

Каждая возможность имеет статус `Unknown`, `Advertised`, `Verified` или `Unsupported`, основание и ограничения. Успешное чтение таблицы не делает её запись `Verified`. Отдельные возможности: `keymap.read`, `keymap.write`, `fn.read`, `rt.write`, `analog.snapshot`, `analog.stream`, `lighting.static`, `lighting.stream`, `lighting.persisted_animation`, `host.digital_rules`, `host.input_suppression`.

Идентификация учитывает VID/PID, product string, служебную коллекцию, поля manufacturer/product и версию протокола. Новая неизвестная ревизия допускает диагностическое чтение по совместимому формату, но не получает все SET-возможности только по совпадению VID/PID.

Компилятор профиля возвращает для каждой функции `Device`, `Host` либо `Unavailable(reason)`, расход аппаратных ресурсов и нормализованный результат. Недоступное аппаратное правило нельзя молча переносить на компьютер: такое изменение влияет на работу без приложения и задержку. UI показывает предложенный вариант явно.

<a id="data-flow"></a>
## Data flow

### Настройка устройства

1. HID discovery находит кандидатов; пользователь выбирает устройство при неоднозначности. Прикладной слой открывает один сеанс и читает identity/capabilities.
2. Протокольный адаптер последовательно читает блоки и возвращает raw-снимок и декодированную модель. Снимок привязан к идентичности, ревизии и времени.
3. Редактор изменяет Draft локально. Rust проверяет инварианты; Vue показывает ошибки рядом с полями. Ползунки не отправляют SET при каждом движении.
4. `validate` строит ChangePlan: затронутые блоки, исходные/новые значения, неизвестные поля, недоступные функции, место исполнения.
5. `apply` повторно проверяет сеанс и актуальность исходного состояния, сохраняет recovery-снимок и исполняет план последовательно.
6. Каждый блок перечитывается и сравнивается. Частичный результат отражается в ApplyReport; UI получает «проверено чтением», «не совпало» либо «результат неизвестен».
7. После переподключения отдельно проверяется сохранение в устройстве. Исходный снимок не заменяется черновиком до успешной проверки.

### Помощник

1. Windows input adapter получает события с идентичностью источника; подтверждённый аналоговый адаптер в будущем добавляет измерения с меткой времени и качеством.
2. Rust-нормализатор формирует InputEvent и передаёт его RuleEngine. UI не участвует в критическом пути.
3. Engine обновляет конечные автоматы нажатий, активные программные слои и условия контекста; выдаёт ActionIntent.
4. ActionDispatcher проверяет доступы, дедупликацию и лимиты; исполняет действие через Windows adapter или отдельный процесс расширений.
5. Результаты и прореженные метрики поступают в UI. При отключении устройства/остановке RuleSet отменяются таймеры и освобождаются синтетически удерживаемые клавиши.

### Подсветка

1. Сцена вычисляет цвета по геометрии клавиш и монотонному времени.
2. Статическая сцена компилируется в аппаратный блок и проходит обычный Apply.
3. Программная анимация возможна только при подтверждённом временном RGB-канале. Кадры передаются с ограничением частоты; устаревшие кадры заменяются последним.
4. Частые SET постоянных цветов не используются как неявный поток анимации, пока не установлен режим записи в память.

## Ключевые интерфейсы

Ниже контракты проектирования, не реализованный код.

| Порт / контракт | Вход → выход | Обязательная семантика |
|---|---|---|
| DeviceDiscovery | enumerate → DeviceCandidate[] | Все подходящие пути без автоматического выбора первого |
| DevicePort | inspect/read_block/apply_patch → Result | Только семантические операции, без произвольных команд из UI |
| HidTransport | open_path/write_report/read_timeout/close | Один владелец, корректное завершение |
| ProfileRepository | load/save/list/recover | schemaVersion, атомарная замена документа, резервная копия |
| InputSource | subscribe → InputEvent | Источник, метка времени, тип, состояние качества |
| RuleEngine | event + runtime state → ActionIntent[] | Детерминированность при заданных времени и порядке |
| ActionExecutor | invocation + cancellation → ActionResult | Ограничения времени и прав, явный результат |
| Clock | now/schedule | Монотонное время; подменяется в тестах |

DTO-запросы Tauri: `devices_list`, `device_connect`, `device_read_snapshot`, `profile_load`, `draft_validate`, `draft_apply`, `operation_cancel`, затем `runtime_start/stop`. Потоковые события: `device_status`, `operation_progress`, `capabilities_changed`, `runtime_diagnostics`, `key_visual_state`. Реальные имена фиксируются при реализации контрактов.

DomainError отличается от TransportError. Ответ IPC содержит стабильный код, сообщение, operationId, recoverability и ограниченный контекст. Сырой пакет и stack trace доступны только в диагностике.

## Предлагаемая структура кода

```text
Cargo.toml                    workspace

  device/ configuration/ lighting/ automation/ actions/
  application/ ports/ types/
crates/io-platform/src/
  hid/ protocols/io_vision_v0/ windows/ storage/
crates/io-cli/src/             диагностика без UI
src-tauri/                    composition root, IPC, tray
src/
  features/device/ configuration/ lighting/ automation/ profiles/
  shared/keyboard-view/ contracts/ stores/
docs/                         решения и протокол
```

`io-core` не зависит от Tauri, hidapi, Windows или Vue. `io-platform` зависит от core и реализует его порты. CLI и Tauri собирают реализации. Отдельный crate для каждого контекста на старте не требуется. Скриптовый worker добавляется только в фазе расширений.

<a id="runtime"></a>
## Семантика помощника и производительность

В v1 остаётся один процесс Tauri с Rust-runtime и tray: закрытие окна может скрывать редактор, явный «Выход» прекращает помощник. Настройка автозапуска отключена по умолчанию. Переход к отдельному пользовательскому агенту допустим позже, если нужны независимые обновления и жизненный цикл; Windows service не вводится без необходимости.

Однократное/двойное нажатие требует политики: немедленное одиночное действие не может одновременно означать взаимоисключающий double tap без ожидания или компенсации. У правила задаются окно распознавания, поведение первого нажатия, удержания и автоповтора. Аккорды задают порядок, окно и условие отпускания. Порог глубины требует гистерезиса и валидной телеметрии.

Raw Input даёт события от конкретного устройства и фоновое получение, но сам по себе не обеспечивает глобальное подавление ввода в других приложениях. [Модель Raw Input](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-raw-input). Маршрут через F13…F24 рассматривается после проверки remap на IO; эти клавиши могут использоваться другими приложениями. Low-level hooks и корреляция устройств не объявляются надёжной заменой filter driver без отдельного эксперимента.

Синтетический ввод должен отмечаться и исключаться из рекурсивного запуска правил. `SendInput` ограничен уровнем целостности целевого процесса; ошибки передаются пользователю. [Документация SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput).

Дискретные переходы нажатия/отпускания не теряются молча. При переполнении очереди — остановка соответствующего runtime и освобождение синтетического состояния. Телеметрия для UI может прореживаться; телеметрия для правил требует сохранения порядка/пересечений порога либо явного состояния потери данных. После reconnect старые таймеры и события не исполняются.

Начальные цели измерений: p50/p95/p99 event-to-action для цифровых правил, стабильность 60-минутной работы, отдельный тест отключения и сна. Численный SLA устанавливается после измерений. Ограничение UI 30–60 обновлений/с — проектная цель, не результат измерений устройства.

<a id="failures"></a>
## Режимы отказа

| Сбой | Влияние | Обработка |
|---|---|---|
| Неизвестная ревизия | Нельзя гарантировать SET | Диагностика и ограниченные capabilities |
| Устройство занято сайтом/другим процессом | Open или обмен может не работать | Понятная ошибка, закрыть другой конфигуратор, повторить |
| Отключение в середине применения | Частичное состояние | ApplyReport, снимок до операции, перечитывание |
| Тайм-аут / поздний ответ | Неясное завершение | Остановить очередь, восстановить сеанс, не повторять SET вслепую |
| Неверный адрес/длина | Риск повреждения модели | Ошибка декодирования; raw сохраняется, запись блокируется |
| Повреждённый профиль / новая схема | Нельзя безопасно загрузить | Проверка схемы, backup, явная миграция |
| Нет живого analog | Не исполняются правила глубины на ПК | CapabilityUnavailable, цифровые правила остаются |
| Зависший скрипт | Блокировка действия | Отдельный процесс, deadline, отмена и завершение |
| Сон/смена контекста/выход | Зависшие удержания | Cancel и best-effort release; ошибки видны |

<a id="scope"></a>
## Вне области v1

Собственная прошивка и OTA, kernel/filter driver, гарантированное глобальное подавление клавиш, бесконечные аппаратные слои, перевод хода в физическую силу, маркетплейс и облачная синхронизация, Bluetooth/2.4G и полная мультиплатформенность. Программные анимации и аналоговые правила включаются только после проверки канала. Их отсутствие не блокирует выпуск конфигуратора с подтверждёнными функциями.
