# Возможности SN34F280 и пределы IO Type 84

Оценка на 2026-09-14 для IO Type 84 Magnetic White, публичного HEX 1.17 и
подключённого ранее экземпляра `0C45:80D6`. Область: клавиатурная логика, API,
аналоговый ввод, RGB клавиш и отдельная LED-полоса. Это оценка реализуемости;
новые функции устройства этим документом не объявляются готовыми.

**Семейство SN34F280 идентифицировано с высокой уверенностью по коду, но точный
установленный MCU ещё не подтверждён маркировкой или производителем. По ресурсам
семейства большинство желаемых функций выглядит реализуемым. Основные препятствия
сейчас — доступ к штатному тракту ввода, гарантии телеметрии, безопасное обновление
и восстановление, а не очевидная нехватка вычислительной мощности.**

Связанные документы: [три уровня интеграции](../INTEGRATION.md),
[новые сведения о flash/security](sonix-manual-safety.md),
[что запросить у производителя](manufacturer-request.md).

## 1. Насколько доказана модель

`SN34F280` — название семейства. В официальном DFP есть `SN34F289F`, `SN34F288F`,
`SN34F2881F`, `SN34F287F`, `SN34F2871F`, `SN34F285J`, `SN34F2851J`, `SN34F2852J`.
Корпуса и выведенные периферийные сигналы различаются. Фраза «на плате точно
SN34F280» недостаточно точна для выбора распиновки и программатора.[^1]

| Свидетельство | Что доказывает | Чего не доказывает |
|---|---|---|
| Startup IO, MMIO, IRQ, `USER_MODE_FLAG` совпали с DFP | Бинарная совместимость с семейством значительно вероятнее альтернатив | Суффикс корпуса, ревизию кристалла и PCB |
| Штатная ветка WASM использует модель SN34F280 | Согласуется с идентификацией по ARM-коду | Defaults загрузчика сами по себе не определяют MCU |
| Родственный OpenAula работает с этой платформой | Есть полезный пример расширения OEM firmware | Одинаковые платы, ADC/mux, LED и адреса hooks |
| VID/PID и версия устройства | Привязку наблюдений к IO White 1.17 | Производителя кремния: USB identity задаёт firmware |
| Маркировка корпуса / BOM производителя | **Пока отсутствуют**; нужны для окончательного выбора part/package | Даже маркировка не измеряет фактические частоты и свободную память |

Проверяемая цепочка изложена в [карте памяти](mcu-memory.md), исходные образы и
хеши — в [манифесте](../evidence/firmware-research-sources.json).

Не предлагать «прочитать CHIPID и закрыть вопрос». В SVD поле `SCU_CHIPID`
отмечено read-only, а руководство 1.7 описывает защищённую запись и использование
в RTC; начальное значение `0x4281` не является таблицей идентификаторов корпусов.
Отдельный Unique Number идентифицирует экземпляр, но тоже не даёт проверенного
декодирования модели. Подробнее — [противоречия документов](sonix-manual-safety.md#discrepancies).

## 2. Ресурсы и аппаратные ограничения

Официальный DFP и полное руководство Sonix дают следующую основу. **Частота в
спецификации не равна измеренной частоте IO; общий объём не равен свободному.**[^1][^2]

| Ресурс семейства | Следствие для проекта | Что требуется проверить на IO |
|---|---|---|
| Cortex-M4, FPU, MPU; до 192 МГц | Подходящая база для фильтра, автоматов клавиш, ограниченных правил и renderer | Clock tree, загрузку ISR/main loop, ABI/FPU и запас времени |
| 160 КиБ SRAM: 32 + 96 + 32 КиБ | Состояния 84 клавиш, очереди и несколько кадров малы относительно общего объёма | Все стеки, DMA, динамические буферы и обращения через alias |
| 512 КиБ MM: 504 КиБ User + 8 КиБ Boot | Есть пространство для кода и настроек; загрузчик тоже находится во flash | Занятость, размещение данных, защиту; нельзя занимать нули HEX |
| 2 КиБ SM | Отдельные служебные данные, boot/security и уникальные значения | Содержимое конкретного устройства, разрешённый способ чтения |
| Один 12-bit SAR ADC; до 16 внешних каналов | Аналоговый тракт уже есть; 84 клавиши требуют разведения/мультиплексирования | Корпус, датчики, mux, очередность, settling, реальные шум/частоту |
| USB HS, DMA, FIFO | Потенциально достаточно для отдельного analog API и управляющих кадров | Дескрипторы endpoints, скорость соединения, очередь и firmware scheduling |
| SPI, timers, DMA | Штатный вывод 84 клавиш и десяти позиций полосы можно переиспользовать | Физический порядок цветов, ограничение яркости/питания, время кадра |

В таблице корпусов руководство показывает 16 ADC-входов у 289/288, 10 у 287,
9 у 285 и 8 у 2852. Это **один преобразователь с несколькими входами**, а не
16 параллельных АЦП. Каналы конкретной платы пока не установлены.[^2]

В публичном IO HEX явно задано 90 728 байт. Восстановленная начальная RAM занимает
32 328 байт. Ни вычитание этих величин из 504/160 КиБ, ни верх начального SP не
выделяют безопасную область для вставки. Настройки могут занимать промежутки,
DMA — обращаться независимо от CPU, а стеки — расти после запуска.
[Проверка startup](../evidence/firmware-startup-v1.17.json).

### Аналоговый сигнал — положение, а не сила

Магнитный датчик позволяет оценивать ход переключателя. Он не измеряет усилие
пальца после упора. Скорость можно оценить из изменения хода, но дифференцирование
усиливает шум. Точность ADC и шаг настройки 0,01 мм не доказывают точность механики
0,01 мм. Нужны калибровочная кривая, шум, гистерезис, частота выборок и их возраст.

Штатная IO уже содержит фильтр и преобразование ADC в ход. Их разумно сохранить
при первых расширениях. Новые типы переключателей, температурную компенсацию
и «обучение намерению» нельзя обещать только по наличию 12-битного ADC.
В руководстве ADC описаны каналы VDD/VSS; пригодный источник температуры на
плате IO ещё не установлен. [Наш разбор HE](calibration.md).

### Расчётные бюджеты

Это **примеры расчёта**, а не результаты измерения и не принятые product limits.
Воспроизводимые числа — в [свидетельстве](../evidence/chip-feasibility.json).

| Сценарий | Расчёт | Практический смысл |
|---|---|---|
| Все 84 датчика по 8 кГц | 672 000 преобразований/с | При расчётной точке 1 MSPS остаётся около трети времени до учёта mux/других затрат |
| То же, четыре выборки на датчик | 2 688 000 преобразований/с | Не помещается в точку 1 MSPS; нельзя одновременно обещать любой oversampling и 8 кГц всей матрицы |
| Цикл обработки при 192 МГц и 8 кГц | 24 000 CPU cycles на весь период 125 мкс | В них должны уложиться все участвующие обработчики, а не только новое правило |
| Полная матрица `84 × u16` по 1 кГц | 168 000 байт/с до заголовков | 64-байтового канала с 1 000 reports/с недостаточно; HS сам по себе не исправляет serializer |
| Полоса, 10 RGB по 60 кадров/с | 1 800 байт/с до заголовков | Для уведомлений не нужна высокая полоса пропускания |
| Все 94 логических RGB по 60 кадров/с | 16 920 байт/с до заголовков | Размер данных невелик; важнее время вывода и приоритет ввода |
| Состояние по 32 байта на 84 клавиши | 2 688 байт | Десятки состояний и таймеров не требуют большого ОС runtime |
| 32 слоя по 128 четырёхбайтовых назначений | 16 384 байта | Пример ёмкости таблиц, не обещание 32 слоёв в stock |
| Два RGB-кадра по 94 позиции | 564 байта | Без учёта штатных planes, encoder, DMA и протокола |

Точку 1 MSPS руководство иллюстрирует для MCLK 16 МГц и 16 тактов преобразования;
это не частота каждой клавиши. У IO надо измерить весь тракт с переключением mux.
Не следует превращать рекламные «8 кГц USB» в «84 независимых датчика по 8 кГц».[^2]

Для гипотетического канала 64 байта верх арифметики составляет 64 000 байт/с при
1 000 reports/с и 512 000 при 8 000. Это сценарии, не измеренные endpoints IO.
Наблюдалось 19 833 FB-пакета за 20 с, только два адреса и ход до 0,18 мм;
экстраполировать это на одновременное движение всех клавиш нельзя.

## 3. Где реализовать запрошенные функции

**A** — настройка stock; **B** — фоновый помощник без перепрошивки;
**C** — расширение firmware. «Возможно C» ниже означает инженерную оценку,
а не уже существующую capability. Физическое исполнение многих stock-назначений
ещё требует приёмки, даже если их байты записаны и прочитаны обратно.

| Функция | Что доступно / путь без новой firmware | Что требует C и почему |
|---|---|---|
| Индивидуальный порог, Rapid Trigger | A: штатные таблицы и редактор | Новые фильтры, адаптивные пороги и иная последовательность обработки |
| DKS, Mod Tap, Toggle | A: штатные форматы | Произвольный граф глубины/времени, больше действий и комбинации сверх кодека |
| SOCD, Rappy Snappy | A: известные штатные режимы | Произвольные группы/политики, velocity priority и явные правила конфликтов |
| Protection Mode | A: можно заранее сделать соседние клавиши менее чувствительными | Динамически менять допуск перед HID, в зависимости от соседей, с release/hysteresis |
| Tap Dance | B: распознать серию и вызвать действие ОС; исходные нажатия остаются | Автономная замена одиночного/двойного/удержания, без утечки промежуточных клавиш |
| Combo | B: наблюдать комбинацию и вызвать действие | Поглотить составляющие до HID, решить перекрытия комбинаций и порядок отпусканий |
| Leader | B: последовательность для команд помощника | Автономная последовательность с подавлением составляющих, тайм-аутом и отменой |
| One-shot, Repeat, Auto Shift, Key Overrides | Часть поведения можно выразить stock-назначениями; полного аналога не установлено | Надёжно изменять итоговые modifiers/key reports до ОС; хранить владельцев удержаний |
| Дополнительные слои | B: слои правил/действий помощника; A: известные Main/Fn | Новые автономные таблицы, переключение, transparent/fallback и хранение |
| Макросы-последовательности | A: записываются в устройство в известном формате | C не требуется ради уже поддержанной последовательности |
| Макросы с условиями/событиями | B: полноценные сценарии ОС и сервисов | Для автономных условий по клавишам/времени — ограниченный исполняемый формат в MCU |
| Аналоговый gamepad | B: телеметрия → виртуальный контроллер, после приёмки потока | Прямой USB gamepad без helper: дескрипторы, оси, отключение цифрового дубля, scheduler |
| Открытый Analog SDK | B: API над проверенной телеметрией; возможен plugin к Wooting SDK | Если stock FB не даёт нужной полноты/частоты — новый пакетный поток со временем/sequence |
| Профиль по активному приложению | B: ОС знает foreground process; host-правила переключаются в RAM | Для аппаратной части нужен штатный volatile selector либо новое volatile API; наличие stock такого API не доказано |
| RGB уведомления на T, музыка | B + stock 32 после проверки карты/TTL/возврата | C полезно для надёжного владения сценой и полного API, если stock ограничивает сценарий |
| LED-полоса, свои автономные сцены | Штатные режимы/функции есть; прямой host setter не найден | Узкое API полосы или локальный renderer; готов offline-прототип, не перенос на плату |
| MIDI, кисть/скролл/скорость камеры | B через SDK и adapter приложения, после проверки analog | C нужен только для автономного USB-интерфейса/правил, а не для каждого приложения |

Готовые QMK реализации показывают, что Tap Dance, Combo, Leader, One-shot,
Repeat, Auto Shift и Overrides — практичные конечные автоматы. Их семантику и
тестовые случаи стоит переиспользовать; наличие Cortex-M4 не делает IO автоматически
QMK/Vial-совместимой. Порт требует драйверов платы, USB, storage и сохранения HE,
а при заимствовании кода — соблюдения его лицензии.[^3][^4][^5][^6][^7][^8][^9]

### Protection Mode: где проходит необходимая граница

У SteelSeries пользователь отмечает защищаемые клавиши; нажатия соседних снижают
их чувствительность. Это ориентир поведения, не доказательство устройства
внутреннего алгоритма SteelSeries.[^10]

Для IO предлагается: выбрать защищаемую клавишу или группу, определить соседей по
**физической геометрии**, задать обычный и защищённый пороги и время возврата.
Например, для R временно требовать большего хода, когда E/T/F удовлетворяют условию.
Числа должен предлагать UI с preview, но исполняться правило должно в RAM MCU
до выдачи обычного HID. Конкретная реализация ещё не выбрана.

Нужно заранее решить: что делать с уже активной R; когда повышать порог при
одновременном движении; как взаимодействовать с RT; не блокировать ли намеренный
Combo. Для уже активной клавиши нельзя просто менять порог каждый кадр — это
может породить ложный release или повторный press. Целесообразен отдельный допуск
первого срабатывания с сохранением правил отпускания. Проверить все порядки событий.

Фоновая программа, получившая `R down` после ОС, не отменяет уже совершённое
действие. Постоянная запись SET порога поверх нажатий даёт задержки и, если путь
сохраняющий, износ flash. Отдельный input filter мог бы перехватывать ввод на ПК,
но это другая сложность и не автономная защита клавиатуры.

### Глубокое PgUp → громкость: два разных сценария

«При глубоком PgUp добавить Volume Up» можно сделать B после подтверждения
телеметрии, оставив обычный PgUp. «При неглубоком нажатии только PgUp, при глубоком
только Volume Up» требует отложить/разрешить первое действие до отправки или
проверить, что нужную семантику полностью выражает stock DKS. Нельзя обещать второй
сценарий только потому, что первый запустился. Чистый выбор по глубине иногда
неизбежно добавляет ожидание: будущее глубокое нажатие ещё не известно при первом
пересечении порога.

То же относится к Tap Dance и Combo: нулевая задержка одиночной клавиши и
гарантированное подавление этого же нажатия при будущем double tap несовместимы
без заранее определённой стратегии. Настройка должна показывать эту семантику,
а не только миллисекунды.

### Analog SDK и gamepad

Wooting Analog SDK уже имеет Rust-компоненты и интерфейс plugins для других
аналоговых устройств. Это более короткий путь к совместимым приложениям, чем
изобретать весь SDK заново. Нужен IO plugin либо мост к единственному владельцу HID
в нашем worker; два независимых клиента не должны конкурировать за поток.[^11]

Контракт IO должен различать raw ADC, нормализованный ход и HID output, сообщать
timestamp, sequence, полноту snapshot и stale/unplug. Неизвестная клавиша не равна
нулевой глубине. Без device timestamps host может сообщать только время получения;
нельзя выдавать его за момент измерения. Сначала доказать releases и одновременный
ход всех клавиш, затем объявлять SDK пригодным для управления.

Оси gamepad потребляют мало данных после обработки на устройстве. Главный риск —
согласованность осей/клавиатуры и совместимость с играми. Обычный HID gamepad
**не становится XInput** от смены имени/VID; XInput не принимает произвольные
DirectInput-устройства. Виртуальное устройство Windows — отдельный adapter;
Microsoft VHF требует kernel-mode source driver, установки и подходящего пути
распространения. Для самого конфигуратора такой драйвер не нужен.[^12][^13]

### Условия и события в макросах

Для MCU разумен ограниченный интерпретатор: события press/release/depth/timer,
булевы условия, несколько переменных, команды key/media/layer/scene/host-action-id.
Нужны пределы числа правил, очереди, шагов на tick и повторов; ожидания выполняются
через таймеры, не busy loop. Владение каждой удерживаемой клавишей учитывается,
чтобы завершение одного макроса не отпустило клавишу другого.

Каталог действий и редактор могут оставаться общими. При сохранении компилятор
раскладывает правило по месту исполнения и отказывает с понятной причиной,
если устройство не поддерживает условие. Это направление развития, не новый
принятый бинарный формат. Не помещать Lua/Python/JS или сетевой LLM runtime в
маленькую вставку только ради универсальности.

Word, shell, HTTP, Telegram, почта, LLM и условия Windows/Linux/macOS остаются
в помощнике. Клавиатура передаёт идентификатор действия или получает состояние.
Она не знает foreground process, учётную запись почты и «сообщение прочитано»
без компьютера. Windows notification listener требует capability и разрешения;
удалённый toast не является подтверждением прочтения сообщения в сервисе.[^14]

## 4. Что меняют исходники производителя

| Полученные материалы | Что реально упростят | Что останется |
|---|---|---|
| Только ещё один HEX | Сравнение версий и статический анализ | ABI, имена, карта данных, recovery |
| ELF/AXF с symbols и MAP | Нахождение callbacks, границ функций, статических объектов и стека | Исходная логика, toolchain, runtime-память и аппаратная приёмка |
| Исходники без SDK/библиотек/проекта | Понимание алгоритмов и форматов | Может быть невозможно собрать точный образ |
| Полный собираемый проект именно White 1.17 | Штатные callbacks/API, карта, безопасная вставка модулей, диагностика | Проверка сборки, timings, recovery и реальные датчики |
| Проект + BSP/схема + ISP/security/recovery + права | Наиболее полезный комплект для поддерживаемой firmware | Интеграция, тесты и сопровождение всё равно нужны |

Исходники особенно ценны для калибровки и USB lifecycle. Они позволяют расширить
имеющийся renderer и таблицы, сохранив проверенный драйвер HE. Но исходники не
содержат автоматически индивидуальную калибровку проданного экземпляра и не
заменяют его backup. Критерий полезности комплекта — сначала воспроизвести
известную сборку или получить объяснимый diff секций, а не просто увидеть `.c`.

Если IO не может передать OEM-код, полезнее запросить документированное API или
официальную сборку с небольшим расширением: полоса/клавиши в RAM, полноценные
analog snapshots, временный профиль, контролируемая доставка host-action.
[Готовый запрос](manufacturer-request.md) содержит этот запасной вариант.

## 5. Насколько сложны пути разработки

Оценки относительные, для нашей базы; сроки до получения материалов и измерений
не назначаются. «Небольшой код» не означает «небольшая проверка».

| Путь | Сложность | Основание |
|---|---|---|
| Развивать штатный конфигуратор | Низкая/средняя относительно firmware | HID, codec, snapshot/diff/readback уже существуют; нужны полнота и физическая приёмка |
| Самостоятельный host worker, процессы, уведомления | Средняя | Rust/OS adapters без MCU-порта; lifecycle, права, очереди, отсутствие UI |
| Узкий API полосы при полном исходном проекте | Средняя | Можно встроиться в штатные callbacks/renderer и точно выделить память |
| То же через бинарную вставку | Высокая до появления recovery | Найдены IO call sites и encoder, но ABI/RAM/linking/reset остаются открыты |
| Protection/Combos/условные макросы с исходниками | Средняя/высокая | Алгоритмы компактны, но затрагивают все press/release и их конфликты |
| Эти же функции через всё больше hooks в HEX | Высокая и растущая | Зависимость от версии, неизвестных инвариантов и взаимодействия stock логики |
| Прямой USB gamepad/LampArray | Высокая | Дескрипторы, endpoint/FIFO budgets, suspend/resume, совместимость ОС |
| Полная замена firmware/QMK-порт | Очень высокая сейчас | Потребуется перенести BSP, HE, storage, USB, LED, boot/recovery; одного ядра ARM мало |

Rust `no_std` подходит для ограниченного движка/API; отдельная ARM-библиотека
уже собиралась. Это не HAL для Sonix и не готовый firmware target. Для сохранения
OEM-кода сначала разумно использовать его C/SDK и узкую границу с Rust, проверив
Thumb, alignment, soft/hard-float ABI, FPU context и linker map.
Tauri/TS/Vue исполняются на компьютере, а не в MCU.

Узкое API полосы — обоснованный первый кандидат: оригинальный encoder в эмуляции
уже изменял только десять выходных позиций и возвращался к stock-кадру. Но это не
доказательство безопасности обновления. [Контракт и результат](panel-host-api.md).

## 6. Что нужно для безопасной работы

1. **Идентичность платы:** маркировка MCU и PCB, корпус, схема или проверенная
   разводка датчиков/mux/LED, BOOT/SWD и уровни питания.
2. **Собираемая программная база:** точный OEM-проект либо согласованный SDK/API;
   версии компилятора/библиотек, linker/scatter, ELF/MAP и лицензии.
3. **Recovery отдельно от работающей клавиатуры:** совместимый Sonix debugger/writer,
   адаптер к установленным площадкам, независимый ввод в BOOT, известный штатный
   boot image или восстановление производителя. Аппаратный BOOT зависит от Code Option.
4. **Backup с покрытием:** User, Boot, доступная SM/Code Option, calibration и
   настройки. Два совпадающих чтения с хешами; защита не снимается ради backup.
5. **Стенд:** запасная плата той же ревизии, измерение питания/уровней, возможность
   проверить scan/HID/LED timing. SWD достаточно для части задач; proprietary writer
   может использовать дополнительные линии. Его контакты нельзя угадывать.
6. **Приёмка восстановления:** возврат после плохого user image, потери USB,
   прерывания обновления и питания, затем сохранность калибровки и полный тест ввода.

Это конкретные зависимости C, а не требование покупать всё для A/B.
Нет подтверждения, что любой ST-Link/J-Link и любая площадка с похожим названием
подойдут. Не подавать питание программатора на плату до проверки VTref/земли/
разводки; внутренние 1,1 В в таблице flash — не напряжение питания IO.
[Подробности recovery и защиты](sonix-manual-safety.md).

## 7. Реальные пределы гибкости

- **Конечные ресурсы.** Нельзя обещать неограниченные слои, пары, скрипты и частоту
  одновременно. Лимиты нужно измерять и возвращать через capabilities, а не
  прибивать к UI по рекламным числам.
- **Память настроек ≠ ресурс чипа.** Две штатные карты, лимит advanced-назначений
  и 512-байтовый writer приложения не описывают весь потенциал MCU. Но увеличивать
  эти размеры без формата/адресов нельзя.
- **Доступ к ОС.** Уведомления, приложения, сеть и актуальное состояние сервисов
  требуют помощника. Новая firmware не отменяет платформенные ограничения ввода;
  например, Windows `SendInput` ограничен UIPI.[^15]
- **Управление ≠ наблюдение.** RGB preview не является измерением света.
  Прочитанный framebuffer сообщает команду renderer, но не доказывает, что LED
  физически горит: оптическая обратная связь не установлена.
- **Сохранение не бывает «каждый кадр».** Runtime-параметры/сцены держать в RAM;
  явное сохранение — отдельно. Ограничение flash касается задержек, износа и
  обрыва питания, а не только числа байтов.
- **Семантика составных действий.** Уже отправленный key-down нельзя отменить
  задним числом; Tap Dance/hold требуют политики ожидания. Нужно тестировать
  rollover, пары на границе порогов, sleep/unplug и конкурирующие макросы.
- **Восстановление не гарантируется USB.** Название Boot ROM не означает
  неуничтожаемую mask ROM. Code Security может уничтожить boot-код при смене уровня.

## 8. Что принять перед обещанием новых возможностей

| Вопрос | Проверка | Результат для продукта |
|---|---|---|
| Точный MCU/PCB? | Маркировка + сведения производителя | Профиль совместимости и конкретная распиновка |
| Полный analog? | Все 84 адреса, ход/отпускание, одновременные клавиши, timestamps/jitter | Реальная частота и границы SDK/жестов |
| Есть запас исполнения? | Clock tree, worst-case scan/ISR, стеки/DMA с RT+RGB+макросами | Бюджет правил и допустимый FPS |
| Можно восстановить? | Защита/BOOT/backup и испытания на запасной плате | Разрешение планировать hardware port; текущий запрет прошивки сохраняется |
| Есть volatile-профиль? | Источник/trace именно операции, отсутствие FMC writes | Безопасное аппаратное app switching; иначе остаются host-профили |
| Узкий LED API работает? | ABI/link map, parser bounds, lease/reset, проверка физического кадра | Отдельная capability полосы |
| Сложные правила не портят ввод? | Конфликтные последовательности до HID, все key-up, bounded runtime | Принятые автономные шаблоны |

Приоритет исследования C: получить комплект производителя → закрыть recovery →
узкое API света/телеметрии → автоматы до HID. Полный firmware rewrite имеет смысл
обсуждать после этих результатов. Направления A/B продолжаются независимо.
