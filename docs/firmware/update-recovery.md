# Обновление, откат и восстановление

Статически разобран путь **IO White 1.17**, состояние 2026-09-14. Ни одной команды
ISP на устройство в этом этапе не отправлялось. Ни успешное обновление, ни recovery
на нашей плате пока не доказаны.

Получен полный [Sonix manual v1.7](sonix-manual-safety.md). Он устанавливает
существенный риск: CS1→CS0 стирает User, CS3→CS0 стирает также Boot. Значения
защиты IO и семантика USB Code Option остаются неизвестными. Автоматическое
снятие защиты ради чтения недопустимо; BOOT P1.3 зависит от BOOTPINEN и сохранности
загрузчика. Общая документация FMC не заменяет спецификацию USB ISP.

## Какой загрузчик используется

[update.json](https://web.io.vision/update.json) выбирает для White `isHex: true`.
В этой ветке сайт передаёт HEX в
[Sonix WASM](https://web.io.vision/assets/sn_isp_lib_bg-DOswDDJh.wasm).
Поля `hexType` и `csType` в записи White отсутствуют; рассмотренные defaults
выбирают SN34F280 и вариант security 0. Поэтому общий перечень SDK-команд
`FLASH_DOWNLOAD 4F`, OTA `80…86` не описывает фактическую ветку White.
Исходники загрузчика сохранены локально; [хеши и воспроизведение](REPRODUCING.md).

```mermaid
flowchart LR
  HEX[Официальный HEX] --> LOAD[HEX loader в WASM]
  LOAD --> IMG[504 КиБ USER ROM]
  IMG --> ISP[ISP state machine]
  ISP --> USB[Feature reports]
  USB --> GATE[Обработчик IO]
  GATE --> ROM[Переход в Boot ROM]
```

Выполнен только участок `HEX → loader → буфер` в окружении без USB/host imports.
Последующие шаги изучались как код, а не исполнялись.

## Вход со стороны firmware IO

1. USB report callback `0x1376C` обрабатывает Feature report и вызывает сравнение
   `0xF4D8` с `AA 55 A5 5A FF 00 33 CC`.
2. Совпадение устанавливает бит `0x10` по RAM-адресу `0x2000006C`.
3. Периодический сервис `0x4F60` выполняет подготовку, очищает запрос и останавливает
   watchdog через `0x2188`.
4. `0x1D8` выключает SysTick, маскирует NVIC и передаёт управление на Thumb-адрес
   `0x00200301`. Boot ROM отсутствует в доступном HEX.

Это отдельный путь от конфигурационного AA/55. Он не устанавливает доступность
нужного интерфейса из Windows и не гарантирует повторное обнаружение после сбоя.
Не переносить из AULA номер интерфейса 3 или boot PID `0C45:7210` без проверки IO.

## Что готовит штатный загрузчик

[Изолированное исполнение реального HEX-loader](../evidence/firmware-isp-payload.json)
показало полный буфер 516 096 байт: отсутствующие адреса заполнены **нулём**,
таблицы калибровки содержат 128 пар defaults 2200/1900, последнее слово —
`0xAAAA5555`. Python независимо воспроизвёл SHA-256 и сумму `0x9BEE`.
Проверялся текущий default-профиль WASM; другие chip/security варианты не обобщаются.

В основном ISP flow WASM (`f_bb`, результат WABT) найден порядок:

| Шаг | Наблюдение в коде host | Что ещё неизвестно |
|---|---|---|
| Entry magic | Feature report, ID 0, дополнение до 64 байт | Фактический ISP interface IO |
| `01` | Запрос версии/параметров загрузчика | Ответ именно нашего Boot ROM |
| `02` | Операция над Code Option; WASM называет ошибку `CodeoptionErase`, OpenAula — compare | Точные побочные эффекты; считать безопасным чтением нельзя |
| `03` | Отправка Code Option/security; в выбранной ветке поле security равно 0 | Соответствие USB поля режимам CS; актуальный RDP IO. По manual снятие CS может стирать User/Boot |
| `04` | Erase от 0, поле count `0x1F8` = 504 | Полная семантика ROM; отображение в физическую flash |
| `05` | Program от 0, count `0x1F80` = 8064 | Поведение при прерывании |
| Data | 8064 блока по 64 байта | Не выполнялись передача/аппаратная сверка |
| Completion | Проверка 16-битной суммы LE-слов | Это не криптографическая подпись и не полный readback |
| `07` | Возврат в user mode | Работоспособность после конкретного сбоя |

Найденный путь передаёт весь USER ROM. Индивидуальное сохранение таблиц IO перед
этой передачей не установлено: стандартный образ содержит defaults. В UI сайта
есть промежуточный callback 100% передачи; он не заменяет завершённую проверку ISP.

Единицы различаются: поля ISP соответствуют 504 блокам по 1 КиБ, прикладной writer
IO выполняет read-modify-write по 512 байт, официальный SWD FLM стирает шагом 4 КиБ.
Нельзя использовать одну из этих величин как универсальный erase size.

## Какие резервные копии нужны

| Материал | Есть сейчас | Что восстанавливает |
|---|---|---|
| Официальный HEX White 1.17 с SHA-256 | Да | Штатный публичный образ с defaults |
| Raw GET snapshot настроек IO и recovery приложения | Да | Прочитанные конфигурационные блоки; не всю flash |
| Профиль пользователя JSON | Да | Поддержанные поля профиля, не уникальные данные MCU |
| Индивидуальные таблицы датчиков всех слотов | Нет | Заводскую/последующую калибровку конкретной платы |
| Полный установленный USER ROM | Нет | Точное исходное состояние этой области |
| Boot ROM, Code Option/security, SM/trim | Нет | Идентификацию загрузчика и сведения о служебных областях |
| Проверенный внешний recovery для нашей PCB | Нет | Возврат при неработающей пользовательской прошивке |

«Backup → flash → restore» в OpenAula означает работу с настройками, а не наличие
полного recovery image со всеми индивидуальными данными. В его flasher обнаружены
изменяющий `dry run` и нефатальная ошибка проверки; [разбор](../reference-projects/OPENAULA.md).

## Downgrade

В рассмотренной ветке сайта есть выбор по версии, а явная host-проверка
криптографического anti-rollback не установлена. Это **не доказательство**, что
Boot ROM примет старую или изменённую прошивку. Нужны старый официальный образ
точно той же аппаратной ревизии, различия схем настроек и проверка версии самого
загрузчика. Переход между версиями может сбросить калибровку/настройки даже при
успешном запуске кода. Готового и проверенного downgrade сейчас нет.

## Условия перехода к аппаратным экспериментам

Сначала идентифицировать PCB/MCU и пути BOOT/SWD, получить документацию о protection
и erase, сохранить доступные уникальные данные. Команды чтения тоже должны быть
проверены по реализации, особенно если библиотека автоматически делает unlock.
Не применять mass erase для снятия защиты: такая операция не создаёт backup.

Карта чтения MM/SM и Code Option теперь описана в [sonix-manual-safety](sonix-manual-safety.md).
Она не создаёт HID read API. При недоступном чтении MM в CS1/CS3 нужен экспорт
производителя или проверенный сервисный путь; не делать destructive unlock.

Полезен второй экземпляр той же ревизии для проверки восстановления. На нём нужно
показать возврат штатного образа после отказа приложения и после прерванной записи,
проверить питание/повторное обнаружение и настройки после перезапуска. Без такого
испытания корректный статический flasher остаётся непроверенным на железе.

Будущий flasher должен иметь чистый offline plan, проверку модели/ревизии/хеша,
раздельные операции настройки защиты, журнал прерывания и обязательную финальную
сверку. Неудача сверки не должна превращаться в «успех» или автоматически запускать
непроверенный образ. Политика выхода из ISP определяется состоянием записи и
подтверждённым поведением Boot ROM. Реализация flasher на этом этапе не начата.
