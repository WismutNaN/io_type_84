# Материалы для запроса IO / OEM

Подготовлено 2026-09-14. **Ниже проект обращения; он никому не отправлен.**
Цель — безопасное открытое приложение для существующей firmware и небольшой
дополнительный API, если штатного недостаточно. Полная замена firmware не является
обязательным условием сотрудничества.

## Текст обращения

Здравствуйте!

Я владелец IO Type 84 Magnetic White и разрабатываю открытое настольное приложение
для её настройки на Rust/Tauri. Первая платформа — Windows, проводное подключение;
в дальнейшем планирую Linux/macOS. Сейчас устройство сообщает firmware 1.17,
USB VID/PID `0C45:80D6`; используется официальный файл
`IO_Type_84_Magnetic_White_V1.17.hex`.

Хочу сохранить штатную обработку магнитных датчиков, калибровку и базовые режимы,
расширив доступ приложения к аналоговым данным, подсветке клавиш и отдельной
LED-полосе. Фоновое приложение будет выполнять действия ОС, управлять уведомлениями
и формировать сцены. Нужна возможность безопасно вернуться к штатной работе.

Просьба помочь со следующими материалами, по возможности для точной ревизии White:

1. **Аппаратная платформа.** Полное обозначение MCU, ревизии PCB/кристалла;
   схема или описание цепей BOOT, SWD, RESET, питания, ADC/mux, датчиков и LED.
   По бинарному анализу вероятно семейство Sonix SN34F280, но корпус не подтверждён.
   Есть ли различия между White/Black и партиями этой модели?
2. **Собираемый проект 1.17.** Исходники приложения firmware, BSP/HAL, все
   библиотеки, точные версии компилятора/SDK/DFP, параметры сборки, linker/scatter,
   startup, итоговые ELF/AXF/MAP и эталонный HEX. Можно ли собрать тот же образ
   вне внутренней среды OEM, и что потребуется для этого?
3. **Штатный протокол.** Описание vendor HID AA/55: настройки, Main/Fn, RT/DKS/
   MT/TGL/RS/SOCD, макросы, типы действий, индексы клавиш/LED, пределы таблиц.
   Какие команды временные, какие сохраняют flash, какие имеют скрытые побочные
   эффекты? Есть ли опубликованный SDK или исходники protocol layer?
4. **Аналоговые данные.** Полная карта 84 клавиш/128 слотов, формат FB и режимы
   streaming, максимальная частота, timestamps, одновременные клавиши, release,
   raw ADC/ход и источник для LED-индикатора глубины. Есть ли готовый snapshot API?
5. **Подсветка.** Карта цветов клавиш и десяти логических позиций полосы,
   порядок каналов, renderer callbacks, таймеры и ограничения питания. Есть ли
   временная отправка кадров полосы и возврат в штатный режим? Можно ли отправлять
   кадры без записи flash, включая явный release/тайм-аут при потере приложения?
6. **Профили в RAM.** Есть ли переключение временного профиля/слоя или временные
   пороги без переписывания flash? Нужна смена по активному приложению и автономные
   условия до отправки обычного HID; сохранять состояние на каждое нажатие не планирую.
7. **Калибровка и индивидуальные данные.** Где хранятся заводские и пользовательские
   параметры каждого датчика, trim самого MCU, серийный номер и Code Option?
   Как их экспортировать без изменения и проверить полный охват? Какие значения
   обновляются автоматически, что сохраняет/сбрасывает штатное обновление?
8. **Boot/ISP и восстановление.** Версия и образ именно установленного Boot,
   спецификация USB ISP и команд Code Option, актуальные Sonix programming/security
   manual и errata, штатные RDP/BOOTPINEN. Нужен способ узнать защиту без unlock/erase.
   Руководство SN34F280 предупреждает о стирании User при CS1→CS0 и User+Boot
   при CS3→CS0: какие операции реально выполняет ваш обновлятор?
9. **Сервисный путь.** Точные compatible debugger/writer, версия ПО, распиновка
   площадок и последовательность восстановления при повреждённом User и при
   повреждённом Boot. Нужны read-only/export и offline plan, без автоматического
   снятия защиты. Доступен ли запасной PCB той же ревизии для испытаний?
10. **Откат.** Официальные образы прошлых совместимых версий, ограничения по PCB,
    схема миграции настроек и калибровки, наличие подписи/anti-rollback и процедура
    возврата после прерванного обновления.
11. **Условия открытой разработки.** Какие исходники/SDK, определения протокола,
    заголовки и изменённые бинарные образы разрешено публиковать и распространять?
    Если части принадлежат OEM/Sonix, можно ли связаться с ответственным разработчиком
    или получить разрешённую для публикации обёртку/API?

Если передача полного исходного проекта невозможна, буду благодарен за
**документированный протокол и официальную firmware с узким расширением**:

- версия/список capabilities и предельные размеры;
- временные кадры отдельно для клавиш и полосы, TTL/явный release, возврат stock
  при USB reset/suspend/отключении приложения;
- snapshots аналоговых значений с sequence/time и явным состоянием отпущенных клавиш;
- временное переключение конфигурации без записи flash;
- опциональные события host-action и управление тем, выдавать ли исходный HID;
- read-only диагностика и поддержанный backup/recovery.

Действия ОС и сервисов останутся в приложении. Самостоятельно менять Code Option
или прошивать непроверенный образ до выяснения восстановления не планирую.

Спасибо! Готов предоставить версию приложения и обезличенные сведения о
подключении, чтобы уточнить совместимость.

## Как оценивать полученный ответ

| Ответ | Что проверяем дальше |
|---|---|
| Ссылка на веб-конфигуратор | Просим протокол/сервисные материалы: сайт уже исследован |
| ZIP с `.c/.h` | Наличие всех библиотек/toolchain/linker, лицензий и эталонной сборки |
| ELF/MAP без исходников | Сверяем SHA/revision; используем символы для анализа, не объявляем восстановленный source |
| Firmware SDK/API | Проверяем no-flash semantics, reset/TTL, bounds и справку о версиях |
| «Восстановите через BOOT» | Уточняем BOOTPINEN, запасной путь при стёртом Boot и сохранность calibration |
| «Unlock для backup» | Просим альтернативный экспорт: unlock может стирать исходные данные |
| Данные под NDA | Отделяем непубликуемые материалы от открытого проекта, согласуем разрешённые производные |

Не нужно запрашивать приватные ключи подписи: если они необходимы для официальной
цепочки, нужен поддержанный путь подписания/тестовой сборки, а не передача ключей.
Окончательную лицензию продукта выбирать по фактически полученным компонентам.
