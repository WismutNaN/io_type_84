# SN34F280: flash, служебные данные и восстановление

Проверено 2026-09-14 по полному [руководству Sonix v1.7, 2025-05-08](https://www.sonix.com.tw/webapi/fl219527/SN34F285_V1.7_EN.pdf).
569 страниц, SHA-256 `1ad200500f9a5c2a4a59dc3ee938809fb4519eb7204627ec4ecdc2ca5fd9e08e`.
Старые `download/file?...` возвращали HTML/ошибки; актуальный URL содержит
`SN34F285`, но документ охватывает семейство SN34F280.
[Файл и воспроизведение проверки](../evidence/chip-feasibility.json).

**Это описание семейства, не измерение защиты установленной IO. Новые операции
на клавиатуре не выполнялись. Руководство не заменяет USB ISP protocol manual.**

## 1. Boot ROM здесь не означает неизменяемый загрузчик

Руководство относит Boot и User к программируемой Main Memory (MM).
Название ROM используется и для flash. Таблица адресов на с. 49, 529, 531–534:

| Область | Физическое чтение CPU | Адрес FMC для program/erase | Размер |
|---|---|---|---|
| Boot | `[0x00200000, 0x00202000)` | MM `[0, 0x2000)` | 8 КиБ |
| User | `[0x00202000, 0x00280000)` | MM `[0x2000, 0x80000)` | 504 КиБ |
| SM / information block | `[0x00400000, 0x00400800)` | Отдельно выбранная SM, не MM | 2 КиБ |
| Shadow User при REMAP=1 | `[0, 0x7E000)` | Не адрес записи shadow | Alias User |

Эта карта объясняет обнаруженное смещение `+0x2000` в FLM и переход IO на
`0x00200301`. Публичный HEX содержит User в логических адресах и не является
полным образом MM. Отдельно надо получить Boot, доступные SM и настройки защиты.
Просто дописать HEX нулями нельзя.

При REMAP=0 область от нуля начинается с Boot, при REMAP=1 — с User. Следовательно,
чтение «от нуля» без зафиксированного remap не определяет, что именно скопировано.
Для программы чтения потребуются явные адресные пространства и длины.

## 2. Снятие защиты уничтожает данные

С. 546–547, §22.8.5 описывают CS0, CS1 и CS3. Визуально проверен текст переходов
на с. 546; таблица на с. 547 и описание erase на с. 537 согласуются с ним.

| Состояние / переход | По руководству | Следствие для IO |
|---|---|---|
| CS0, RDP не `5A`/`A5` | Debug/Writer может читать MM и обращаться к SRAM | Может позволить backup; состояние IO неизвестно |
| CS1, RDP `5A` | Debug чтение MM и доступ к SRAM запрещены; SM читается | Нельзя включить обычное чтение без изменения защиты |
| CS3, RDP `A5` | Аналогичные ограничения debug; переход CS3→CS1 запрещён | Не считать CS3 эквивалентом CS1 при восстановлении |
| CS1→CS0 | Стирается User, Boot сохраняется | Уничтожается исходная firmware/калибровка User |
| CS3→CS0 | Стираются User **и Boot** | Можно потерять USB recovery вместе с пользовательским кодом |

Понижение CS — не downgrade версии firmware. Статус RDP, Code Option и версия
Boot у нашей клавиатуры пока не прочитаны. `csType=0` в defaults сайта не является
наблюдением CS0 в устройстве. Соответствие поля WASM низкоуровневой операции RDP
ещё нужно подтвердить по загрузчику.

Если инструмент предлагает unlock при неудачном чтении, нельзя принимать его
автоматически. Получить полный backup при CS1/CS3 обычным SWD-чтением может быть
невозможно. Тогда нужен документированный экспорт производителя/работающей
firmware или запасная плата с известным восстановлением; неизвестные данные не
заменяются defaults.

В нормальном исполнении код может читать MM, согласно таблице с. 547; это
**не означает наличие команды чтения через штатный HID**. Ради экспорта нельзя
сначала прошить потенциально разрушающий исходное состояние модуль.

## 3. SM, Code Option и BOOT

С. 531 задаёт четыре страницы SM по 512 байт:

- Page 0/1 зарезервированы производителем; изменять их нельзя.
- Page 2 содержит RDP/Boot Byte и резерв. Байты RDP и Boot представлены с
  дополнительными копиями/инверсией, обслуживаются специальными FMC messages.
- Page 3 — customer use. Наличие этой страницы не даёт разрешения использовать
  её для приложения: назначение на IO неизвестно.

В §2.9, с. 66 `BOOTPINEN` расположен в Code Option по `0x00400500`, bit 2,
default 1. В §23.4.2, с. 552 BOOT P1.3 low при старте удерживает исполнение
загрузчика и не даёт user firmware выключить SWD P3.5/P3.6. **Работоспособность
такого входа зависит от сохранного Boot и Code Option**, а не только от доступности
площадки на плате. Default в manual не равен прочитанному значению IO.

§2.10, с. 66 описывает уникальный номер экземпляра двумя 32-битными словами
`0x00400180` и `0x00400190`. Это часть SM Page 0, а не адрес разрешённой записи.
Он не является документированным кодом модели. Boot Byte выбора remap, BOOTPINEN
и последнее слово User `0xAAAA5555` — разные сущности.

Не переносить калибровку другого экземпляра вместо своей. Клавишные min/max
из User — отдельны от уникального номера, Code Option и возможных заводских
настроек аналогового блока. Полный состав последних для IO по-прежнему неизвестен.

## 4. Сохранение настроек влияет на latency

На с. 529 сказано, что CPU останавливается на program/erase. §22.8.4, с. 545
уточняет варианты AUTO_HOLD: работа из SRAM возможна при специальных условиях,
но доступ к MM/SM другими участниками и обработчики прерываний требуют согласования.
Нельзя просто перенести одну функцию записи в RAM и обещать непрерывный HE scan.

Таблица с. 559: 512-байтовая page; typical erase 10,6 мс, program 3,8 мс,
endurance min 10K / typical 100K erase+program cycles. Эти значения приведены
Sonix как ориентиры проектирования; собственные latency/endurance IO не измерены.
Не выдавать typical за гарантированную верхнюю границу задержки.

Практические выводы:

1. Анимации, Protection и быстрые смены контекста используют RAM; flash нужна
   для явного сохранения, а не каждого tick.
2. Переписывание страницы при каждом переключении окна не подходит как основной
   механизм аппаратных app profiles. Нужен volatile selector либо host-only профиль.
3. Для будущего хранилища нужны транзакции/две копии, generation/CRC и восстановление
   после потери питания. Наличие spare flash не доказывает dual-bank boot/failover.
4. Состояния и счётчики событий не должны постоянно изнашивать одну страницу.

На с. 529 также указано: erased flash заполняется **0**, не `FF`. Это объясняет,
почему нулевая заполненность не даёт оснований считать область code cave или
полным backup. Поведение конкретной операции всё равно проверяется по её пути.

## 5. Не смешивать три протокола

| Интерфейс | Что документировано / разобрано | Что нельзя из этого вывести |
|---|---|---|
| Stock IO AA/55 | Настройки, FB и часть света | Произвольное чтение MCU или FMC |
| USB ISP сайта | Host state machine и переход IO в Boot | Полное поведение boot-кода, сохранность SM/Boot при командах `02/03` |
| FMC messages в manual | Внутренние MMIO операции CPU над flash | Что одноимённый/однономерный USB пакет делает то же самое |

Например, внутренний FMC `0x6` получает status RDP, а `0x4` меняет защиту.
Эти номера **не являются командами HID allowlist**. Даже получение статуса FMC
требует обращений к регистрам и запуска message; оно не разрешается в нашем
диагностическом режиме автоматически по названию «read».

§22.7 на с. 535 упоминает UART0 boot loader. В IO код и сайт ведут к USB ISP.
Нужна версия и документация именно установленного Boot; универсальный текст
manual не доказывает ни доступный UART recovery IO, ни точную семантику USB.

С. 560 описывает **Writer**, включая P1.0/P1.1 и P3.5/P3.6; с. 552 — SWD.
Это не один и тот же кабель/режим. Подходящие варианты Sonix SN-LINK/Writer и
пины надо подтвердить у производителя для точного корпуса и PCB.

## 6. Противоречия, которые нельзя скрывать

| Документ | Расхождение | Рабочее обращение с ним |
|---|---|---|
| SVD 2.0.4 и manual с. 89–90/302 | `CHIPID` read-only в SVD, защищённая запись/RPW в manual | Не использовать как неизменяемый part ID; не писать |
| Manual с. 531 | В тексте лишний ноль у начала MM; таблица даёт `0x00200000` | Использовать согласованные таблицы с. 49/533 и проверку FLM |
| Manual с. 532 | На схеме верх alias обозначен `0x7D000`, что расходится с 504 КиБ | PDSC/FLM/таблица: размер `0x7E000`; схему не копировать в код |
| Manual с. 540 | В одном пункте упоминается CS2, тогда как основной раздел даёт CS0/1/3 | Таблица с. 546–547, уточнение у Sonix перед аппаратной работой |
| Manual с. 531 | Строка customer use = Page 3, одна фраза ниже говорит Page 2 | Никакой новой записи SM; запросить актуальное уточнение |
| Manual с. 191/193 | Ограничение MCLK записано `<16 MHz`, пример 1 MSPS использует 16 MHz | Это ориентир расчёта, не настройка частоты IO; запросить рабочий режим/errata |

Вычисление границ и SHA не заменяет аппаратного доказательства; наличие
569-страничного manual не означает, что «чип полностью изучен». Остались:
точный part/revision, clock tree IO, boot/security, board wiring, реальные budgets,
калибровка и безопасный readback. [Матрица закрытия](chip-feasibility.md#8-что-принять-перед-обещанием-новых-возможностей).

## 7. Условия безопасного следующего этапа

Нужны точная плата и уровни питания, экспорт SM/security без unlock, проверенный
полный backup доступных областей, исходный Boot или сервисное восстановление,
официальный compatible writer/SDK. Затем — стенд на запасной PCB и приёмка
восстановления с неработающим User. На пользовательской клавиатуре никаких
новых операций этот документ не разрешает.

Критические страницы 30, 531, 546, 559 и 560 проверены также изображениями PDF;
остальные указанные разделы прочитаны в извлечённом тексте. Полный PDF, текст и
рендеры остаются в игнорируемом `archive_data`; в Git — выводы и хеши.
