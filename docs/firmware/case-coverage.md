# Применимость hardware_case и software_case

Состояние 2026-09-14. Исходные файлы владельца сохранены без изменений в
`archive_data/hardware_case.md` и `archive_data/software_case.md`; хеши в
[свидетельстве](../evidence/chip-feasibility.json). Это идеи и ссылки на чужие
продукты. Их предлагаемый порядок реализации не заменяет принятый план A/B/C.

Главная [оценка MCU и функций](chip-feasibility.md) содержит Protection, DKS/RT,
SOCD, Tap Dance, Combo, Leader, One-shot, Repeat, Auto Shift, Overrides и макросы.
Здесь — оставшиеся сценарии и существенные поправки, чтобы их не потерять.

## Аппаратные сценарии

| Группа из hardware_case | Реализуемость и условие |
|---|---|
| Порог/RT/мёртвые зоны | A в рамках найденного кодека. Параметр сайта и физический порог должны проверяться отдельно |
| Velocity, направление, траектория хода | B или C; сначала точность/частота/time. Шум производной и пропуски могут делать жест неоднозначным |
| Глубина как слой, analog Combo | C для автономного действия до HID; B для добавочного действия ОС после приёмки analog |
| MIDI velocity/aftertouch | B → MIDI adapter. Значение «aftertouch» синтезируется из хода, не измеренного усилия после упора |
| Analog gamepad, кисть, jog, scroll | API и adapter получателя; программа должна принимать параметр. Нельзя добавить полноценный analog API в любое приложение одной клавиатурой |
| Switch selector, калибровка, фильтры | Существующие HE routines сохранить. Для новых switches нужны совместимая механика/магнит/датчик и проверенные кривые |
| Температурная компенсация | Источник температуры и модель IO неизвестны; название настройки не создаёт измерение |
| Noise, распределение хода, графики | Возможны по достоверным данным; значения ±0,018 мм из case — пример, не измерение IO |
| Adaptive actuation / обучение ошибкам | Отдельная исследовательская функция с подтверждением пользователем; намерение пальца не наблюдается напрямую |
| Динамические слои и «неограниченные» пары | Ресурсы конечны. Формат, limits, пересечения и scheduler нужны даже при большой свободной памяти |
| Режим совместимости для игр | Явно отключаемые автоматизации и проверяемый профиль; нельзя гарантировать принятие всеми играми/правилами |

## Программные сценарии

| Группа из software_case | Исполнение и ограничения |
|---|---|
| App/window profiles | B: foreground adapter + профиль правил в RAM. Чтобы менять аппаратные пороги, нужен отдельно подтверждённый volatile API |
| Контекст вкладки/документа/выделения | Adapter или plugin конкретного приложения, не сведения, которые MCU может извлечь из клавиатурных отчётов |
| Actions Ring, Fn overlay, экранная подсказка слоя | B: обычный UI overlay; Fn и активный аппаратный слой доступны только при наличии соответствующей телеметрии |
| Процессы, файлы, URL, shell, clipboard, HTTP | Общий ActionCatalog и платформенные реализации. Импорт профиля не запускает команды |
| Последовательности, условия, отмена, ожидания | Host runtime с bounded queue/deadline/cancel. Сетевые операции не блокируют HID |
| Состояния mute/recording/media | Получать actual state через provider; слепой toggle не доказывает результат |
| Звонки и временный рабочий слой | Overlay с приоритетом и восстановлением предыдущего профиля; зависит от события звонка/состояния приложения |
| Telegram/почта/уведомления | Providers на ОС/сервисе. Toast listener не даёт универсального unread count и требует permission/capability |
| Свет T, прогресс, таймер, Git/build | B → сцена с TTL, priority и явной поверхностью. T/полоса проходят разные capabilities и приёмку |
| Музыка / экран / ambient | Анализ на ПК, кадры или компактные параметры эффекта в устройство. Не передавать аудиопоток в MCU ради цветов |
| Windows Dynamic Lighting / LampArray | Отдельная интеграция; скрытый handler в HEX не равен объявленному USB-интерфейсу |
| Локальный REST/WebSocket API | Возможный adapter к тому же worker; версии, права, limits и стабильные ID. Сервер не обязателен для базового пользователя |
| Интеграции iCUE/GameSense/Stream Deck | Рассматривать их официальные SDK/providers по конкретному сценарию; они не делают IO совместимой автоматически |
| Windows/Linux/macOS варианты действий | Один intent, разные adapters и capability/fallback; сохранённая конфигурация не означает реализованную платформу |

## Что уточнено по первичным источникам

**App linking.** У Wooting v5.4.0 работа разделена между Background Service и
поддержкой firmware 2.14.0. Это подтверждает применимость разделения A/B/C:
ОС выбирает контекст, firmware умеет загрузить соответствующее состояние.
Из этого нельзя вывести наличие такого selector у IO.
[Официальный changelog](https://wooting.io/wootility/changelogs/5.4.0).

**Analog SDK.** Wooting предусматривает plugins; наш IO transport можно адаптировать
после подтверждения потока. SDK не исправляет отсутствующие измерения и не
превращает клавиатуру в gamepad без отдельного consumer.
[Исходники и документация plugins](https://github.com/WootingKb/wooting-analog-sdk/blob/develop/docs/PLUGINS.md).

**LampArray.** Windows имеет API управления такими устройствами, но наш IO не
объявляет найденный в callback интерфейс 4. Host bridge через VHF потребует
отдельного kernel-mode driver; это не небольшая настройка Tauri.
[Microsoft Lighting](https://learn.microsoft.com/en-us/windows/apps/develop/devices-sensors/lighting-dynamic-lamparray),
[VHF](https://learn.microsoft.com/en-us/windows-hardware/drivers/hid/virtual-hid-framework--vhf-),
[IO descriptors](../evidence/firmware-startup-v1.17.json).

**Уведомления.** Listener видит доступные системные уведомления, а состояние
«прочитано в Telegram/почте» требует соответствующего источника. Планировать
отдельные состояния `notification-present` и `service-unread`, а не выдумывать
второе из исчезновения первого.
[Microsoft Notification listener](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/notification-listener).

## Как сохранить понятный интерфейс

Это направления развития уже принятого UI, не новые реализованные экраны:

- Клавиша/группа → условие → действие. Место исполнения и доступность видны до сохранения.
- Простой шаблон скрывает автомат, но даёт preview переходов: что произойдёт на
  лёгком/глубоком нажатии, удержании и отпускании, останется ли исходная клавиша.
- Источники событий, каталог действий и сцены редактируются отдельно; инспектор
  клавиши ссылается на них. В нём не появляется весь workflow editor.
- Полоса и клавиши представлены отдельными поверхностями одной сцены. Слой
  уведомлений временный, после завершения возвращается основная подсветка.
- Диагностика показывает только наблюдённое: stale, неизвестный ход/цвет,
  рассчитанный preview и реальный readback различаются.

В базовом режиме не показывать FMC/Code Option/ABI. Потребность C объяснять
ограничением конкретного сценария; A/B должны оставаться полезными без неё.
