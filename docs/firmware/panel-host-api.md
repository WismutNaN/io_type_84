# Минимальный API для LED-полосы White 1.17

2026-09-14. Цель: приложение ОС рассчитывает уведомления, триггеры и кадры;
клавиатура временно выводит десять цветов и самостоятельно возвращает штатный свет.
Прошивка устройства не изменялась. Исследование и прототип не включают прошивальщик.

## Что уже реализовано в штатной firmware

Драйвер вывода LED, штатные эффекты полосы, отображение хода, преобразование цвета
в передаваемый поток и работа магнитных датчиков уже существуют. Их переписывание
для уведомлений не требуется. Нужно открыть ограниченный доступ к последнему кадру
полосы, сохранив штатную логику работающей в фоне.

Новые доказательства получены после восстановления сжатой начальной RAM:

- Scatter table `0x15C28`: распаковка `0x15C48 → RAM 0x20000000`, 4608 байт;
  затем очистка `[0x20001200, 0x20007E48)`. Python-декодер и оригинальные ARM routines
  в Unicorn дали одинаковые **32 328 байт**. Периферия в эмуляторе не отображалась.
- USB-конфигурация `0x20001168` объявляет четыре интерфейса. Восстановлены
  дескрипторы keyboard/consumer/FF68/FF67, callback SET `0x1376D` по `0x200011F0`.
- Ветка `0x1376C` с первым аргументом **4** похожа на LampArray, но интерфейс 4
  не объявлен. Первый аргумент — индекс интерфейса, не тип Feature report.
  Для интерфейса 3 доступен путь ISP magic. GET callback `0x12C94` также не даёт
  полного набора LampArray attributes. Просто включить стандартное API Windows
  и получить полосу сейчас нельзя.

[Реконструкция startup/USB](../evidence/firmware-startup-v1.17.json).
Для сравнения LampArray использованы [HID Lighting and Illumination](https://www.usb.org/sites/default/files/hutrr84_-_lighting_and_illumination_page.pdf)
и [Windows LampArray](https://learn.microsoft.com/en-us/uwp/api/windows.devices.lights.lamparray).
Референс 105 ламп в RAM относится к этому общему коду, а не карте полосы IO.

## Найденная точка вывода

```text
штатные эффекты клавиш → штатный compositor полосы → AA/55 dispatcher
    → 0x13028: кодирование общего кадра через 0x6C90
    → [предлагаемая подмена только 10 пикселей в выходном буфере]
    → 0x2DCC: передача 0x469 байт
```

`0x6C90(index,c0,c1,c2)` кодирует пиксель в 12 байт по
`0x20004C34 + 1 + index*12`. Таблица кодирования — `0x14A9C`; порядок каналов
в закодированном потоке c1, c0, c2. Физическую цветопередачу ещё нужно проверить.
Штатный вызов передаёт **1129 = 1 + 94×12 байт**: область первых 94 позиций,
включающая 84 клавиши и полосу 84…93. Предварительно кодируются 126 позиций,
но оставшиеся не входят в эту передачу. Это анализ вызова, не измерение SPI на PCB.

Карта полосы из ROM: логические позиции 0…9 → render 93…84. Их выходные байты —
`[1009,1129)`. Названия «левый/правый край» появятся после физического сопоставления.

В изолированной эмуляции вызваны **оригинальные** `0x13028` и `0x6C90`, затем
повторно закодированы только десять позиций полосы. Изменения остались внутри
её 120 байт. Все три штатные RGB-плоскости остались прежними. Следующий штатный
кадр побайтно восстановил исходный вывод. Это подтверждает принцип подмены без
перезаписи настроек и без копирования/восстановления внутреннего состояния эффектов.
[Результат проверки](../evidence/panel-compositor-v1.17.json).

## Минимальное расширение

Две основные точки перехвата вызовов:

| Место | Исходные 4 байта | Штатная цель | Дополнение |
|---|---|---|---|
| `0xF94A` | `FD F7 3B FF` | `0xD7C4` | Обработать собственный envelope; остальные пакеты передать исходному dispatcher |
| `0xF964` | `03 F0 60 FB` | `0x13028` | Сначала штатный encoder, затем десять вызовов `0x6C90`, если lease активна |

Это кандидаты call sites, не готовый бинарный патч. Адрес вставки, RAM для состояния,
trampoline/ABI и обработка USB disconnect/suspend ещё должны быть привязаны и проверены.
Кодировать пиксели после штатного encoder проще, чем менять compositor `0xEEA0`:
не затрагиваются эффекты, индикация глубины, настройки и буферы RGB клавиш.

Контекст dispatcher: RX `0x2000637C`, TX `0x2000633C`, RX-ready `0x2000036F`,
TX-ready `0x2000036E`. Собственный пакет перехватывается **до** штатного обработчика;
ответ использует существующий TX-путь. Обработка пакета и композиция идут в основном
цикле. Тяжёлая логика ОС, скрипты и обработка аудио сюда не переносятся.

## Контракт прототипа v1

Для изолированного прототипа выбран envelope на **`0x33` с сигнатурой `IOLQ`**.
На штатном White 1.17 команда 33 возвращает эхо и исключена из ветки прерывания
макрорежима вместе с 32. Это лучше кандидата 3E: даже probe 3E мог бы пройти через
общую ветку прекращения удерживаемого действия. Legacy 33 без сигнатуры остаётся
штатным. Это частное расширение модели IO, не стандарт производителя.

Запрос CAPS исполнен в оригинальном `0xD7C4` в изолированной эмуляции при установленном
флаге удерживаемого макроса. Получено ровно эхо с заменой AA на 55; флаг сохранился.
Все записи ограничились TX-ответом, ready-флагами и стеком. Вызова flash/USB/SPI
не было. Это проверка конкретного пакета на точном образе, не аппаратный probe.

| Байты 64-байтового пакета | Значение |
|---|---|
| 0 / 1 | `AA / 33`; в ответе `55 / 33` |
| 2 | Длина payload: CAPS 4, FRAME 44, RELEASE 12 |
| 3…4 | Transaction ID, u16 LE, только наш envelope |
| 5 | CAPS=1, FRAME=2, RELEASE=3; в ответе `op | 0x80` |
| 6 / 7 | `1 / 1`: один законченный пакет, версия протокола |
| 8…11 | `IOLQ` в запросе, **`IOLR`** в ответе |
| 12…15, 16…19 | FRAME/RELEASE: session token u32, sequence u32 |
| 20…21 | FRAME: lease TTL, 100…2000 мс |
| 22…51 | FRAME: десять RGB-троек, весь кадр одной транзакцией |
| Остаток | Нули; ненулевые reserved/padding отклоняются |

Ответ содержит status по байту 12. CAPS дополнительно возвращает 10 пикселей,
минимальный/максимальный TTL, три канала, признак временного вывода и идентификатор
ABI. Host проверяет версию, opcode, transaction, сигнатуру и длину. Штатное эхо
не может включить capability: в нём нет `IOLR` и response opcode.

Последовательность: CAPS → FRAME с новым ненулевым token → следующие FRAME → RELEASE.
Первый кадр получает временное управление. Чужая session при активном владельце
отклоняется. Повтор старого sequence не продлевает TTL. RELEASE закрывает текущую
session; поздние её кадры не возобновляют свет. Один worker владеет транспортом,
очередь хранит только последний кадр, а остановка имеет приоритет.

Прототип помнит последнего владельца. Token не является секретом или механизмом
аутентификации; после смены нескольких владельцев история старых tokens не хранится.
При истечении TTL следующий новый sequence текущей session может возобновить поток,
а после явного RELEASE/disconnect требуется новый token. Переполнение sequence
требует смены session. ACK FRAME подтверждает принятие кадра в RAM, не физический вывод.

На каждом выводе проверяется истечение TTL. При остановке кадров применяется
штатный результат. Источник времени — штатный счётчик через `0x2170` (SysTick);
обработка suspend/disconnect обязана сбрасывать lease отдельно. Во время калибровки
и аппаратной диагностики host-наложение должно уступать штатной индикации.
Яркость ограничивается модельным adapter, с учётом штатной яркости полосы
`0x20000303`; геометрия и порядок физических каналов пока не приняты.

## Граница с приложением

```text
Telegram/почта/аудио/жест
  → правило и приоритет в приложении
  → renderer сцены: десять RGB-троек
  → LightingStreamPort (capabilities, frame, release)
  → адаптер IO и общий HID worker
  → временная подмена выходного кадра полосы
```

RGB клавиш остаётся отдельной поверхностью. У существующей команды 32 найден
таймер: 50 периодов по 2000 вызовов scheduler снимают флаг `0x2000036B`;
зависимость от реального времени ещё не измерена. Пустой пакет 32 **продлевает**
режим, а не освобождает его. Приложение не должно выдавать эти таймеры за точный TTL
нового API. Индексы вне 0…127 не используются: handler не проверяет таблицу достаточно
строго и может попасть в соседние ROM-данные; это не путь управления полосой.

Узкий API даёт компьютеру цвета, срок владения и освобождение поверхности.
Он не принимает адреса RAM/flash, исполняемый код, прошивку, произвольные размеры
таблиц или команды калибровки. Пользовательский интерфейс по-прежнему оперирует
событиями, цветами и сценами. Отдельный редактор прошивки для этого не требуется.

## Готовность

Принцип подмены подтверждён на оригинальном ARM encoder в эмуляторе. Протокол и
lease проверяются отдельным программным прототипом. Нативный transport не отправляет
этот envelope и не заявляет поддержку полосы. Для применения на устройстве остаются
проверка ABI/памяти/времени, сборка минимальной вставки, физическая карта и recovery.
Готового изменённого HEX и результата прошивки нет.

[Код и команды проверки](../../experiments/panel-api/README.md): восемь Rust-тестов,
Clippy и сборка `no_std` библиотеки для `thumbv7em-none-eabi` прошли. Размер состояния
в host-примере — 48 байт без heap; стек и обёртки ещё не рассчитаны.
[Контекст приложения и критерии интеграции](../../modules/lighting-stream.md).
