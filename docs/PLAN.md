# План реализации

Стек: Rust + Tauri 2 + TypeScript + Vue 3. Первая платформа: **Windows + USB, подтверждено пользователем**. Проект открытый; платформенные адаптеры должны позволять добавление других ОС. Фазы ниже — проект последовательности, не выполненные работы. Каждая оставляет запускаемую систему. Размер фазы ориентировочно 1–5 рабочих дней одного разработчика; при превышении объёма фазу разделить до начала реализации, не скрывать незавершённость.

Обновление 2026-09-14: native open/GET и SET/readback/restore основных блоков подтверждены. Vue-редакторы реализованы. FB получен, полный физический тест остаётся; RGB streaming не проверен. Актуальная матрица — [EDITOR_IMPLEMENTATION](EDITOR_IMPLEMENTATION.md). Незавершённые проверки ниже не становятся выполненными от наличия формы. Свидетельства — [DEVICE_RESEARCH](DEVICE_RESEARCH.md). Для каждой фазы читать указанные модули и её контекст.

## Порядок по целям пользователя

Единая карта исследований и возможностей — [INTEGRATION](INTEGRATION.md).
Три варианта использования закреплены в [ADR-0007](adr/0007-integration-levels.md).
Полный перечень hardware/software cases, готовность и критерии следующих результатов —
[FEATURE_MATRIX](FEATURE_MATRIX.md). После отказа производителя не ожидаем исходников:
выпуск A/B на штатной firmware, [ADR-0008](adr/0008-stock-first-delivery.md).

| Направление | Фазы | Следующий проверяемый результат |
|---|---|---|
| A — штатная настройка | 2–9 | Приёмка выполнения/питания, ёмкости макросов и пробелов редактора; без нового firmware |
| B — помощник на штатной firmware | 10–14 | Самостоятельный lifecycle, цифровые триггеры и запуск заданной программы; затем сложные правила/интеграции |
| C — расширение устройства | Исследовательская ветка 13C → [firmware/ROADMAP](firmware/ROADMAP.md) | После конкретного пробела A/B: API полосы с доказанными ABI/памятью/recovery; аппаратная запись сейчас запрещена |
| Общая приёмка | 15, на каждом выпускаемом уровне | Проверить отдельно конфигуратор, фон и каждую поддержанную firmware |

A и B — приоритет продукта; незавершённый физический эксперимент A не останавливает
программную доработку B. Аналоговый тест фазы 12 не блокирует цифровые правила.
C не является предварительным условием выпуска A/B. Переходы — выбор пользователя,
а не автоматическая смена режима при импорте профиля.

Уточнение после обратной связи о PgUp/PgDn: рекомендуемый первый сквозной результат
на пересечении 10B/11A — [исключающий выбор по глубине](../modules/automation.md#exclusive-depth).
Сначала спецификация цикла и проверка владения исходным вводом, затем реализация
минимального маршрута на stock и приёмка результата в ОС. Фон можно дорабатывать
независимо; расширение каталога и ожидание новой firmware не закрывают этот сценарий.

### Проверка архитектуры objects.md перед реализацией

Владелец допускает сложные жесты/слои в helper, если поведение надёжное. Полный
граф не представим в известных stock-таблицах; это не требует сужения авторской
модели, но требует проверки input/output contract. [Модель](OBJECT_MODEL.md),
[ADR-0009 — предложено](adr/0009-behavior-model-and-execution.md).

- [ ] **M0 / до расширения 11A:** G1 exclusive PgUp/PgDn, G2 два владельца Shift +
  физический ввод, отказ/stop; выбрать stock-маркер или проверяемый готовый backend.
  При неприемлемом результате — оценка узкого C bridge → [gates](objects/COMPATIBILITY.md),
  [миграция](../modules/execution-plan.md).
- [ ] **M1–M2 / 11A:** definitions/runtime, planner с отказом потери семантики,
  один полный ExclusiveDepth и UI; сохранить v2/additive-правила → [execution-plan](../modules/execution-plan.md),
  [automation](../modules/automation.md#exclusive-depth).
- [ ] **M3 / 10–11:** общий runtime, repository/lifecycle, цифровые слои/Flow —
  [companion](../modules/companion.md). Работа над lifecycle не зависит от света.
- [ ] **M4 / 12–14:** analog/targets/providers по отдельным gates; C только при
  доказанном контракте → [firmware contract](objects/FIRMWARE_CONTRACT.md).

Это уточнение последовательности существующих фаз, не новая реализация и не
обещание полного stock-пути. Перед C по-прежнему требуются recovery и отдельная
разрешённая аппаратная сессия; полный firmware runtime не является предпосылкой M1.

- [ ] Процесс с пробелами/Unicode и отдельными аргументами; отсутствующий executable/вариант ОС; отмена не закрывает уже открытый пользовательский документ.
- [ ] Перезапуск и регистрация автозапуска проверены отдельно; импорт не включает исполнение и не создаёт регистрацию.

**Откат:** исходный экспорт v2 сохраняется перед миграцией. Для возврата к старому
EXE отключить новую регистрацию автозапуска, восстановить прежний профиль;
аппаратные настройки не затрагиваются. Каждый 10A/B/C — отдельный проверенный коммит.

<a id="phase-11"></a>

## Фаза 11 — правила и программные слои

**Цель:** single/double tap, hold, аккорды и условия контекста. **Результат:** редактируемый RuleSet с симулятором событий. **Трудоёмкость:** L, два подэтапа по 3–5 дней. **Статус:** [~] Глубина/удержание группы реализованы; цифровые автоматы, взаимоисключающие жесты и слои ещё нет.

**Контекст для агента:** использовать существующий GestureEngine и каталог; цифровой источник добавляет фаза 10B. Несколько текущих порогов независимы, double tap не реализован. Автоматическая смена программного слоя не записывает firmware. Место исполнения слоя показывать явно.

### Задачи

- [ ] 11A: конечные автоматы триггеров и виртуальный Clock; сначала выделенные назначения/добавочные действия. Замена исходного ввода требует отдельной capability, не подразумевается observer → [automation](../modules/automation.md).
- [ ] 11B: программные слои, контекст активного приложения и форма редактора → [automation](../modules/automation.md), [UI](UI.md).
- [ ] Измерить event-to-action и показать конфликты правил → [ARCHITECTURE](ARCHITECTURE.md#runtime), [application](../modules/application.md).

### Проверка

- [ ] Границы интервалов, перекрывающиеся аккорды, отмена таймеров, смена профиля при удержании.
- [ ] 60-минутная работа, нагрузка и переполнение очереди с управляемой остановкой.

**Контекст для агента:** после 66 получен FB по двум адресам до 0,18 мм, stop 67 проверен. Использовать этот путь, не начинать с неоднозначного 68 заново. Датчик силы не установлен; глубина и HID key-down различаются. Эта фаза не блокирует цифровые правила фона.

### Задачи

## Каталог, жесты и события — продолжение

Все hardware/software cases сведены в [матрицу функций](FEATURE_MATRIX.md).
[Оценка MCU](firmware/chip-feasibility.md) остаётся основанием аппаратных ограничений.
Это план, не реализация новых автоматов. Производитель, со слов владельца, материалы
не предоставит; продолжение A/B не зависит от них. C рассматривается для реального
пробела после A/B и требует recovery перед записью. Для B не использовать сохраняющие
SET как быстрый переключатель аппаратных профилей.

**Готово в коде:** каталог действий/варианты ОС, условия по глубине и удержанию группы, общий черновик и profile v2, Windows queue adapter. Контекст: [action-catalog](../modules/action-catalog.md).

**Приёмка:** физический полный ход PgUp/PgDn и одновременных клавиш; непрерывность удержания при simulation; foreground/minimized поведение.

**Следующий этап:** сначала фаза 10 — самостоятельный фон и выбор процесса; затем
11/14 — остальные автоматы, ScriptCatalog и провайдеры операций. Источники
Telegram/почты и LightScene относятся к 13B; поддержка полосы из 13C не блокирует
действия ОС. [ADR-0006](adr/0006-actions-gestures-scenes.md),
[уровни интеграции](INTEGRATION.md). Не добавлять все формы в инспектор клавиши.
