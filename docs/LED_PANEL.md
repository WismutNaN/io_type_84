# LED-панель

Обновлено: 2026-09-14. Самостоятельная часть требований к устройству. Для реализации читать также [модуль подсветки](../modules/lighting.md) и [протокол](PROTOCOL.md).

Для расширения firmware теперь есть [основа OpenAula](reference-projects/OPENAULA.md)
и [официальный SDK Sonix](firmware/mcu-memory.md). OpenAula показывает добавление
своего RGB renderer; управление полосой IO требует отдельного переноса.
В IO подтверждён путь сохранения panel/options в `0x8200`; временный host-канал
полосы пока не установлен. [Разбор](firmware-lighting-v1.17.md).

## Что известно

Владелец подтвердил отдельную физическую LED-панель: в штатной настройке она переливается или показывает нажатие отдельных клавиш. Пользователь хочет менять её поведение, цвета и эффекты из приложения.

Описание «сила нажатия» сохраняется как наблюдение владельца. Физическая сила в ньютонах не измерена; магнитный датчик обычно описывается глубиной хода. Пока не проверены ни единицы индикации панели, ни передача этих данных на компьютер.

Устройство имеет 84 клавиши, таблицы настроек на 128 слотов и отдельную панель. Это разные представления. В статическом анализе 1.17 восстановлено десять логических позиций полосы, индексы общего renderer 84…93. Физическая геометрия, число корпусов LED и направление ещё не измерены. Экран прототипа показывает условную полосу, а не измеренную схему железа.

## Кандидаты для исследования

В общем bundle сайта присутствуют `GET_LIGHT_BOX` (`0x1B`), `SET_LIGHT_BOX` (`0x2B`), `SET_DOT_MATRIX_MODE` (`0x2A`) и механизмы side light (`1D/2D`). Их наличие в общем коде не доказывает, что именно эти команды управляют панелью IO White. Совпадающие функции найдены в HFD SDK, разобранном в [Aether-HE](reference-projects/AETHER_HE.md).

2026-09-13 выполнен фиксированный native probe: точный дескриптор FF68 совпал, GET `10` вернул прежнюю identity и 1.17, затем GET `1B` на 24 байта не вернул ни одного байта за 1000 мс. После этого сеанс остановлен и handle закрыт; повторов и GET `1D` не было. Это отсутствие ответа в конкретном режиме, а не доказательство отсутствия панели или безусловной неподдержки команды. [Сырые запросы/ответы](evidence/aux-lighting-probe.json), [скрипт с ограниченным allowlist](../tools/probe_aux_lighting.py).

Поля light box и side light по коду IO: mode/R/G/B в байтах 0–3, colorMode в 8, brightness в 9, speed в 10; объём 24 байта. Без успешного чтения и физического сопоставления эти поля не становятся capabilities панели. SET `2B/2D/2A` не отправлялись. Следующий шаг — искать фактический путь IO UI/firmware, а не перебирать изменяющие команды.

Публичный bundle сохранён как `archive_data/vendor_site/2026-09-13/layout-classic-DXDjowst.js`. [Профиль пользователя](PROFILE_FORMAT.md) не содержит отдельного блока панели. Поля `ledMaxFrames=0`, `tftMaxFrames=0`, `gifMaxFrames=0` не доказывают отсутствие физической панели или её штатных эффектов.

## Граница в модели

### Найденный штатный путь (2026-09-14)

В `profile.fnKeyList` пользовательского JSON обнаружены `FUNC` назначения:

| Сочетание | Значение FUNC | Название в IO bundle / смысл                       |
| --------- | ------------- | -------------------------------------------------- |
| Fn+G      | 87            | `侧灯RT深度灯效` — свет по глубине RT              |
| Fn+K      | 91            | `灯条叠加模式` — наложение режимов полосы          |
| Fn+L      | 27            | `正面灯条效果切换` — смена эффекта передней полосы |

Это объясняет возможный путь штатного управления без отдельной команды `2B`. Рабочая интерпретация связи с наблюдаемой владельцем панелью остаётся гипотезой до физической проверки сочетаний. Codec назначения — `[0D, value>>16, value>>8, value]` в Fn/base таблице. Эти три действия доступны в каталоге редактора и частичном импорте профиля. Само переназначение не исполняет действие; оно вызывается физическим нажатием.

Код 1 (factory reset), также найденный в Fn+Del профиля, не включён в каталог новых назначений и не запускался. Управление параметрами панели, рисование кадров и геометрия по этим назначениям не восстановлены.

Контекст Lighting получает `LightingSurface`: `KeyBacklight` и `LedPanel`. У каждой поверхности свои topology, capabilities, режимы, адреса, ограничения частоты/яркости и способ исполнения. Сцена адресует конкретную поверхность. Связь панели с клавишами описывается явным отображением, если оно понадобится и будет проверено.

Перелив может исполняться прошивкой. Реакция на ход может исполняться прошивкой без передачи живых измерений в приложение. Программная анимация или правило по глубине на ПК требуют отдельно подтверждённого канала данных. Нельзя выводить наличие одного из другого.

## Порядок дальнейшей работы

1. Определить физическую геометрию и штатное переключение режимов.
2. Статически сопоставить страницу модели, общий bundle и [прошивку](FIRMWARE_RESEARCH.md).
3. Установить подходящий GET и получить исходное состояние панели.
4. Подготовить один проверяемый SET, readback и восстановление; отдельно проверить сохранение после отключения.
5. Реализовать редактор фактически доступных режимов. Поток кадров добавлять только после проверки временного канала и ограничений.

Сейчас есть отдельный раздел UI и переназначение перечисленных штатных функций. Прямое управление физической панелью ещё не реализовано.

## Положение на макете, 2026-09-14

Владелец уточнил: LED-панель находится над стрелками под Del и PgDn. В новом UI эта область размещена внутри физической схемы. Пиктограмма нейтральная: число столбиков, цвета и анимация не выдаются за измеренную топологию или состояние. Протокол прямого управления по-прежнему требует исследования.

## Уточнение по бинарнику, 2026-09-14

[Разбор точного HEX](firmware-lighting-v1.17.md) независимо связал FUNC 87/91/27 с handlers переключения глубины, наложения и эффекта полосы. Восстановлены массивы десяти логических позиций, compositor и пороги заполнения `10,20,…90,95`; единица внутреннего показателя и выбор среди нескольких нажатых клавиш пока неизвестны. Это подтверждает внутреннюю реализацию индикатора, описанного владельцем.

В найденном dispatcher нет GET 1B / SET 2B / SET 2A / SET 2D. Поэтому прежний план «найти подходящий GET из общего SDK» заменяется трассировкой реальных входов к состоянию панели. `0x32` пишет RGB клавиш в RAM, но его карта не адресует полосу. Не расширять диапазон отправляемых адресов и не выдавать этот канал за поддержку панели.

Уведомления должны адресовать как отдельные клавиши (например T), так и полосу через одну модель сцен, при разной доступности исполнителей. Работающие локальные предпросмотры не доказывают физическое выполнение сцены. Проект уведомлений/музыки и восстановления базовой подсветки — [ADR-0006](adr/0006-actions-gestures-scenes.md).
