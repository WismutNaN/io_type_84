# AK820 Pro Modder и Aether-HE: применимость к IO

Проверено 2026-09-13 на локальных ревизиях ниже. Оба проекта полезны как референсы протокола. Ни один в исследованном состоянии не заявляет и не выбирает IO White `0C45:80D6` как поддерживаемую модель. Совпадение протокола настройки не означает одинаковую плату, MCU или совместимую прошивку.

## Результат

| Референс | Что совпало с IO | Что мешает прямому применению |
|---|---|---|
| [AK820 Pro Modder](reference-projects/AK820_PRO.md) | Реальный Rust `build_frame` воспроизвёл **80/80** сохранённых запросов IO; общий набор GET, keymap, информация, lighting, macro | Другая механическая модель; нет адаптера IO/RT; отличаются режимы подсветки, интерфейсные комментарии и проверка ответов |
| [Aether-HE / Mini60 Pro](reference-projects/AETHER_HE.md) | Реальный `build_table_read` воспроизвёл **79/79** обычных GET; **128/128** RT-записей прошли decode → encode | Профиль Mini60 содержит 126 RT/RGB слотов; у IO прочитано 128. `protocol_sonix.py` — другой экспериментальный адаптер |

Совместимость framing проверена исполнением отдельных чистых функций, без запуска приложений и открытия HID. В AK-тест передавались параметры наших запросов, включая payload `68`; этот тест не означает, что AK-приложение само умеет все эти команды. Mini60-тест исключает `68`, поскольку это запрос с идентификаторами клавиш, а не пустой table GET.

Результат воспроизводится из корня через `python tools/compare_reference_codecs.py` при наличии Python, rustc и локальных референсов. Скрипт проверяет SHA-256 исходников, извлекает только рассмотренные функции; не собирает сторонние crates и не импортирует приложения. [Машинный отчёт](evidence/reference-codec-comparison.json).

## Новые направления

- **Live analog:** в обоих SDK есть simulation `66/67` и уведомления `55 FB`. В коде IO найдены те же поля хода и ADC, что в HFD-документе Aether, но stream на устройстве ещё не включался: [разбор](reference-projects/AETHER_HE.md#аналоговый-поток-и-временный-rgb).
- **Временный RGB:** `32`, несмотря на имя `GET_LED_DATA`, в USB-ветке SDK отправляет цвета. Это изменяющая операция; она не входит в allowlist чтения. Перспективнее проверить её отдельно, чем передавать анимацию циклом записей `24`.
- **LED-панель:** новый native probe подтвердил identity 1.17, затем `GET_LIGHT_BOX 1B` не получил ответ за 1000 мс. Сеанс остановлен, `1D` не отправлялся. [Пакеты](evidence/aux-lighting-probe.json), [интерпретация](LED_PANEL.md).
- **Макросы:** сырое поле capacity равно `0x9200`, а значение 512 в профиле может быть подставлено сайтом. Реальный доступный объём ещё не проверен; [протокол](PROTOCOL.md#информация).
- **Железо/QMK:** найдена цепочка AK820 → fpb → SonixQMK, но признаки нашего HEX противоречат простому предположению «тот же Cortex-M0 SN32F299». [Подробности и источники](FIRMWARE_RESEARCH.md#сопоставление-с-ak820-и-sonix).

## Решение для разработки

Продолжать собственный `io_vision_v0`. Параметры IO — identity, интерфейс, размеры таблиц, точность RT, режимы — хранить в профиле устройства адаптера. Общий код framing можно выделить после появления второго проверенного устройства. Сейчас нельзя заменить профиль IO профилем Mini60 или перенести flasher AK820.

Для следующей аппаратной записи сначала реализовать проверяемое чтение на Rust, raw snapshot и минимальный diff/readback/recovery. Для панели сначала локализовать фактическую команду по IO UI/прошивке. Для firmware сначала установить MCU, карту памяти и путь восстановления именно IO. Новые исследования не завершают фазу Rust HID или ручную проверку desktop EXE.

Сторонние приложения и прошивальщики не запускались; SET, simulation, calibration, reset, OTA не отправлялись. В публичном репозитории только наши скрипты, короткие технические свидетельства и документация, не код/бинарники референсов.
