# Исследование прошивки White 1.17

Первичный разбор: 2026-09-13. **Актуальная точка входа — [база firmware](firmware/README.md)**,
обновлена 2026-09-14: найден официальный Sonix DFP SN34F280, разобраны ISP/калибровка
и применимость OpenAula. Этот файл сохраняет начальные наблюдения и ход проверки.
Приложение не обновляет прошивку.

## Источник и воспроизводимость

На [странице настроек производителя](https://web.io.vision/settings) предусмотрено обновление. [Каталог update.json](https://web.io.vision/update.json) содержит запись IO Type 84 Magnetic White, productId 32982, версия 1.17, `isHex: true`. Точное имя позволило скачать [IO_Type_84_Magnetic_White_V1.17.hex](https://web.io.vision/IO_Type_84_Magnetic_White_V1.17.hex) без перебора запросов.

Файл имеет размер **255 277 байт**, SHA-256 `8f5ef507771c6795258eb7521cfc1b46269a5b301548767ae87a3f1a83a50d45`. Версия совпадает с ответом подключённой клавиатуры, но это не доказывает побайтовую идентичность установленной прошивки.

Полный HEX и каталог остаются в игнорируемом `archive_data/firmware/2026-09-13/`. В Git находятся [источник и хеши](evidence/firmware-source.json), [структурный отчёт](evidence/firmware-white-v1.17-analysis.json) и собственный [анализатор](../tools/inspect_firmware.py). Код и бинарник производителя в продукт не включены.

Из корня репозитория, PowerShell и Python 3.10+:

```powershell
New-Item -ItemType Directory -Force archive_data/firmware/2026-09-13
Invoke-WebRequest 'https://web.io.vision/IO_Type_84_Magnetic_White_V1.17.hex' -OutFile archive_data/firmware/2026-09-13/IO_Type_84_Magnetic_White_V1.17.hex
python tools/inspect_firmware.py archive_data/firmware/2026-09-13/IO_Type_84_Magnetic_White_V1.17.hex
python -m unittest discover -s tools -p 'test_*.py'
```

## Измеренные результаты

| Параметр | Результат |
|---|---|
| Формат | Intel HEX, контрольные суммы всех записей корректны |
| Записи | 5677: 5672 data, 3 extended linear address, 1 start linear address, 1 EOF |
| Реальные данные | 90 728 байт |
| Сегмент 1 | `[0x00000000, 0x00016264)`, 90 724 байта |
| Сегмент 2 | `[0x0007DFFC, 0x0007E000)`, 4 байта |
| Start linear address | `0x000001C1` |
| Первое слово LE | `0x20007E48`, похоже на начальный stack pointer |
| Второе слово LE | `0x00000205`, похоже на Thumb reset vector с адресом кода `0x204` |

Сам по себе адресный размах HEX не устанавливает размер flash. Уточнение 2026-09-14:
официальный DFP и фактический WASM loader подтверждают USER ROM 504 КиБ;
последнее слово `0xAAAA5555` определено startup как USER_MODE_FLAG, а не CRC/подпись.
[Карта памяти](firmware/mcu-memory.md). Start linear address и reset vector — разные поля.

В данных найдены USB-диагностические строки `[USBD]` около `0x10184`, `0x101D8`, `0x10228` и строка модели ` IO Type 84 Magnetic White` около `0x10B93`. Первые слова совместимы с таблицей векторов ARM Cortex-M. Пробная дизассемблировка Thumb по адресу `0x204` дала последовательность загрузок/записей и переход `bx r0` по `0x218`; это поддерживает гипотезу об архитектуре, но не определяет точную модель MCU. Анализатор сохраняет только структурные признаки; дизассемблер не является зависимостью проекта.

## Сопоставление с AK820 и Sonix

[Разбор AK820 от fpb](https://github.com/fpb/ajazz-ak820-pro) привёл к QMK-порту и гипотезе HFD80CP100 / SN32F299 для **той** платы. Совпадение с IO на уровне configurator AA/55 не переносит это определение MCU автоматически.

Официальный [SN32F299 manual v1.8](https://www.sonix.com.tw/webapi/fl219869/SN32F299_V1.8_EN.pdf), страницы 16 и 39 PDF: Cortex-M0, flash 256 KiB, SRAM 32 KiB, code flash `[0, 0x40000)`. Начальный SP IO `0x20007E48` укладывается в такой объём RAM, однако это неспецифичный признак. Запись IO HEX по `0x7DFFC` лежит вне этой code flash; назначение четырёх байтов неизвестно, поэтому отдельно этот факт не устанавливает размер памяти/модель чипа. PDF сохранён локально в `archive_data/hardware_sources/2026-09-13/`, не включён в Git.

Более сильное расхождение — код по предполагаемому reset vector IO:

| Адрес | Байты | Thumb-декодирование Capstone 5.0.7 |
|---|---|---|
| `0x208` | `21 F4 80 31` | `bic r1, r1, #0x10000` |
| `0x210` | `4F F4 80 31` | `mov.w r1, #0x10000` |

В [ARM Cortex-M0 Generic User Guide, §3.5.2](https://documentation-service.arm.com/static/5ea6ce5e9931941038def8c1) BIC поддерживается в регистровой форме с обновлением флагов; показанная immediate Thumb-2 форма не соответствует Cortex-M0 ISA. При верном определении таблицы векторов и незашифрованном коде это аргумент **против** прямого отождествления IO с Cortex-M0 SN32F299. Он не позволяет выбрать между конкретными более новыми Cortex-M или назвать OEM.

[Полная короткая последовательность и literal pool](evidence/firmware-reset-analysis.json): код обращается к `0x4001F004` и `0x4001F000`, затем переходит на `0x1C1`. Значение регистров пока не установлено. Воспроизведение: разобрать HEX собственным `parse_hex`, взять `[0x204,0x21A)` и дизассемблировать Capstone в `CS_ARCH_ARM`, `CS_MODE_THUMB | CS_MODE_LITTLE_ENDIAN`. Вектор, адреса и слова проверены статически; flash не читалась и код не исполнялся на устройстве.

[SonixFlasherC](https://github.com/SonixQMK/SonixFlasherC) и AK820 BIN полезны как справочный материал, но их bootloader IDs, erase ranges и offset нельзя принимать для IO. Общий SDK сайта содержит `FLASH_DOWNLOAD 4F` и OTA `80…86`; наличие таких имён не доказывает пригодность конкретного пути обновления. Прежде чем готовить запись firmware, нужны точный MCU/разметка, совместимость образа, способ входа и проверенный путь восстановления именно IO.

## Начальный маршрут исследования

Пункты 1–3 ниже выполнены/уточнены в [новой базе](firmware/README.md).
Дальнейшая работа идёт от [OpenAula и SDK](firmware/ROADMAP.md), аппаратная проверка
остаётся отдельным этапом. Ранние фразы «MCU/назначение регистров неизвестны» выше
описывают состояние до получения DFP, а не текущий вывод.

1. Проверить таблицу векторов, карту памяти и происхождение USB-строк; установить MCU по нескольким независимым признакам.
2. Найти обработчик AA/55 и сопоставить его с уже прочитанными GET и кодом сайта.
3. Исследовать кандидаты команд панели из [LED_PANEL](LED_PANEL.md), сначала статически.
4. Подтверждать аппаратное поведение отдельно: наличие функции в бинарнике не доказывает её доступность этой модели или режима.

Не выполнялись прошивка устройства, запуск бинарника, извлечение flash или пробные SET. Корректная сумма Intel HEX проверяет целостность записи, а не цифровую подпись производителя.
