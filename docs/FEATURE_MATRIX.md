# Функции и план работы без новой прошивки

Актуально: 2026-09-14, IO Type 84 Magnetic White 1.17. Основание —
`archive_data/hardware_case.md` (разделы 1–20 и дополнения),
`archive_data/software_case.md` (разделы 1–15), текущий код и аппаратные свидетельства.
Хеши case-файлов — в [chip-feasibility.json](evidence/chip-feasibility.json).
Идеи из этих файлов не считаются готовыми функциями IO.

Владелец сообщил, что производитель отказал в предоставлении материалов.
Ожидание исходников больше не является следующим шагом продукта. Готовим полезный
выпуск **на штатной firmware**, сохраняя необязательное исследование расширений.
[Решение](adr/0008-stock-first-delivery.md), [общие уровни](INTEGRATION.md).

**Отказаться от перепрошивки в первом выпуске можно. Обещать, что все сценарии,
кроме Protection Mode, уже будут стабильно работать без неё, — нельзя.**
Дополнительные границы: свободное управление полосой, автономность новых автоматов,
замена исходного ввода и полнота analog-потока. Многие ограничения ввода можно
обойти настройкой stock либо отдельным перехватом ОС; это не доказательство
необходимости firmware для каждого такого сценария.

## Обозначения и порядок выбора

- **A:** штатная настройка; исполняется клавиатурой, работает без помощника после
  физической приёмки. Изменение таблиц/макросов не равно замене прошивки.
- **B:** помощник в пользовательском сеансе ОС, без новой firmware. Новые действия
  требуют реализации/приёмки, даже если MCU для них исследовать не нужно.
- **B-перехват:** отдельный необязательный маршрут замены ввода средствами ОС.
  Это часть B с другими ограничениями, не уже готовый Raw Input observer.
- **C:** изменённая firmware для недоступного API или автономного нового поведения.
  Сейчас не устанавливается и не является условием выпуска.

**Р** — есть редактор/codec/runtime; **З** — соответствующие байты реально
записаны, прочитаны и восстановлены; **И** — исследование без аппаратной приёмки;
**П** — предстоит реализовать. З не доказывает воспроизведение и сохранение после
питания. «Без нового реверса» означает, что можно развивать ПО на известных
контрактах; уже проведённый разбор протокола используется.

Предпочтение: штатное назначение → stock-событие как триггер B → наблюдение B →
явно выбранный B-перехват. C рассматриваем только после конкретного неудовлетворённого
сценария. Данные preview и результаты на железе не смешиваются.

## Как обойтись stock-событием вместо полного Analog SDK

Для многих условий нужен факт «достигнут глубокий порог», а не каждая выборка ADC.
Полезный кандидат: **штатный DKS/MT/Fn → выделенный клавиатурный код → действие B**.
Это настройка существующей firmware. F13…F24 — кандидаты после проверки поддержки,
не гарантия отсутствия конфликтов. Их число конечно; сочетания тоже требуют учёта.

В текущем Rust `DksConfiguration.actions` — `[u8; 4]`; это не четыре произвольных
`ActionDefinition`. В UI DKS выбираются keyboard usages. Поэтому запись «macro ID»
или Windows media-команды в этот байт недопустима без доказанного кодирования.
Мост в B позволяет запускать произвольное действие каталога от разрешённого
выходного кода, не выдумывая новый формат DKS.

Для PgUp/PgDn нужно различать три результата:

1. Обычное действие и **добавочное** изменение громкости на глубине — кандидат A→B.
2. Выделенная клавиша только для команд по глубине — кандидат DKS→B; когда B
   выключен, пользователь заранее знает, что эти команды не исполнятся.
3. Лёгкий tap только PgUp, глубокий только Volume Up — требуется проверить
   отложенную семантику stock DKS либо собрать события и решение в B. Уже выданный
   PgUp не отменяется. Выбор может происходить на отпускании/тайм-ауте и иметь задержку.

**Следующая приёмка моста:** один свободный код, одна выбранная клавиша, snapshot,
конкретный diff и restore; проверить press/release, modifiers, повтор, оба слоя,
отключение B и обычный ввод. До этого не объявлять маршрут готовым.
Для velocity/gamepad/траекторий такой мост не заменяет полный analog.

## Где помогает перехват ОС, а где нет

Raw Input даёт источник устройства и события в фоне. Его регистрация не является
глобальным подавлением ввода чужих окон. `RegisterHotKey` подходит для конкретных
shortcut-команд, но может конфликтовать с другими регистрациями и не предоставляет
универсальную матрицу всех клавиш IO.
[Microsoft Raw Input](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-raw-input),
[RegisterHotKey](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey).

`WH_KEYBOARD_LL` позволяет подавить передачу сообщения целевому окну,
но работает с другим событием, не содержащим Raw Input `hDevice`; связать их
по времени не значит доказать устройство. Hook требует быстрого callback и может
быть удалён ОС при тайм-ауте. Это основание для отдельного opt-in adapter и
матрицы совместимости, а не запрет на программные Tap Dance/Overrides. Ожидание
double tap выполняет наш автомат, а не блокирующий callback hook.
[Microsoft LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc),
[KBDLLHOOKSTRUCT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-kbdllhookstruct).

Возможен более глубокий фильтр/виртуальный ввод, но он добавляет установку,
сопровождение и платформенные зависимости. Для начального B используем выделенные
назначения/добавочные действия; перехват букв не включается неявно.
`SendInput` ограничен уровнем целостности процессов, обычный helper не гарантирует
работу во всех повышенных окнах.
[Microsoft SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput).

Перехват ОС не открывает адреса LED-полосы и не добавляет измерений датчиков.
Новая firmware тоже не обеспечивает состояние Telegram/почты без providers на ПК.

## Следующие результаты и критерии

| Шаг | Конкретный результат | Основание / критерий остановки исследования |
|---|---|---|
| N1. Принять штатные функции | Таблица физической приёмки remap/RT/DKS/MT/TGL/SOCD/макроса/полосы и power-cycle с restore | Известные codec и [сценарии проверки](EDITOR_IMPLEMENTATION.md); отказ конкретного режима документировать отдельно |
| N2. Довести фон | Repository + lifecycle без UI + цифровой источник + ProcessAction, pause/tray/autostart | [Фаза 10](PLAN.md#phase-10), [companion](../modules/companion.md). Работает без ожидания N1/analog/прошивки |
| N3. Принять stock→B мост | Один проверенный DKS/MT/Fn trigger и исполняемый пример «глубоко → действие» | [Модуль](../modules/companion.md#stock-trigger). Если codec не выражает событие, не подставлять неизвестные значения |
| N4. Сложные сценарии ОС | Цифровые tap/hold/combo на выделенных триггерах, host-слои по приложениям, условия/результаты | [Фаза 11](PLAN.md#phase-11), [automation](../modules/automation.md). Перехват — отдельная capability, не часть обещания первого B |
| N5. Проверить analog и RGB клавиш | Полный ход/release/concurrency и отдельный RGB 32 с возвратом | [Фаза 12](PLAN.md#phase-12), [13A](PLAN.md#phase-13). При неуспехе ограничить capability; не блокировать цифровые действия |
| N6. Providers и сценарии | Уведомления/контекст/процессы, свет на клавишах после N5, затем audio/SDK/gamepad | [Фазы 13B/14](PLAN.md#phase-13), [actions](../modules/actions.md). Сначала один сквозной provider, не все сервисы сразу |
| N7. Оценить оставшиеся потребности | Реальные неудовлетворённые сценарии и их цена: полоса, автономность, Protection | [Firmware roadmap](firmware/ROADMAP.md). Только здесь возвращаться к расширению; source производителя не ожидается |

Нумерация задаёт приоритет, не цепочку блокировок: разработка N2 возможна сразу,
N1/N3 требуют отдельной наблюдаемой аппаратной сессии. Новых записей на устройство
в рамках этой систематизации не выполнялось.

Выпуск A/B имеет смысл даже при недоступных analog/полосе: законченные штатные
редакторы и цифровые команды/сценарии — самостоятельный продукт. Следующий полезный
инкремент — **N2 и подготовка N1/N3**, а не полный реверс чипа или новый flasher.
