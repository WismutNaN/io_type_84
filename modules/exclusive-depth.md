# Выбор действия по глубине

Реализованный вертикальный сценарий на stock White 1.17: PgUp/PgDn передаются
приложению через штатное назначение без вывода. Прошивка не изменяется.
[Аппаратный захват](../docs/evidence/stock-capture-acceptance-v1.17.json),
[исходный ARM](../docs/firmware/stock-input-v1.17.md).

## Поведение и границы

`DepthChoice` задаёт физический слот, light/deep/release в мкм и два ID каталога.
Это отдельное правило, а не два независимых GestureRule. Лёгкая ветка выдаётся
при измеренном отпускании; глубокая — сразу на пороге, окончательно отменяя
лёгкую для этого цикла. После глубокого удержания и возврата через пороги нет
PageUp/PageDown. Без `deepRepeat` глубокая ветка выдаётся один раз за цикл.

Опциональный `deepRepeat: HoldRepeat { delayMs, intervalMs }` повторяет короткое
действие, пока клавиша остаётся глубоко нажатой. Начальные значения — 350/80 мс:
первый шаг сразу, после паузы — шаг на каждый интервал. Гистерезис выхода 0,20 мм
(не ниже release + 0,10 мм) останавливает повтор без лёгкой ветки. Возврат в глубокую
зону без полного отпускания начинает новую паузу; исходный первый шаг не дублируется.
Потеря свежих пакетов на 100 мс останавливает повтор; полный timeout 600 мс отменяет
весь цикл до измеренного отпускания. Пропущенные интервалы не догоняются пачкой.

Очередь исполнителя хранит не более одного ожидающего повтора на источник. Перед
выдачей проверяются цикл удержания, свежесть данных и возраст шага (<50 мс).
Отпускание/выход из зоны отменяет ожидающий шаг; новый цикл не оживляет старую очередь.
При занятом исполнителе повтор пропускается. Уже переданную Windows пару down/up
отменить задним числом нельзя; реальные задержки ещё требуют аппаратного измерения.

Начальные пороги: 0,60 / 3,00 / 0,20 мм. Данные старше 600 мс отменяют цикл;
после старта, пропуска данных или смены правил нужен измеренный возврат.
Отсутствие пакетов не превращается в отпускание. Решение, не переданное
исполнителю в течение 600 мс, тоже отбрасывается.

Две ветки ссылаются на обычный ActionDefinition: клавиша, media, текст,
приложение или программный макрос с вариантами ОС. Повтор разрешён для клавиши
или повышения/понижения громкости; все варианты ОС должны быть совместимы.
Toggle media, запуск программы, текст и макрос выполняются однократно. Их повтор
требует отдельной политики отмены/повторного входа; текущая реализация не накапливает
макросы за долгим удержанием. Количество взаимоисключающих веток пока равно двум.
Один физический слот не может одновременно принадлежать DepthChoice и
добавочному жесту, в том числе сочетанию. UI явно сообщает, сколько старых
добавочных жестов заменится при сохранении выбора.

Чистая модель допускает другие слоты; stock adapter пока принимает только
105/108 и точную White 1.17. Это область аппаратной проверки, а не предел модели.
Fn не имеет отдельного события в FB: выбор действует одинаково в обоих слоях.
Настройка аппаратного Fn для переданной клавиши временно заменена, после остановки
восстанавливается. Сложные аппаратные пары/advanced-настройки сначала нужно убрать
с обоих слоёв; adapter не разрывает их неявно.

## Применение и восстановление

1. `prepare_automation(profile, baseRevision)` строит план без SET. Если перед ним
   подготовлены аппаратные изменения, используется их целевой снимок.
2. UI показывает две ветки, конкретные клавиши, оба слоя и зависимость от процесса.
3. `configure_automation(profile, enabled, ownershipToken)` сверяет весь профиль
   и токен, повторно читает устройство, сохраняет журнал с `sync_all`, затем
   применяет stock `[5,0,0,0]` и проверяет GET. Наблюдение запускается после записи.
4. Остановка, apply, reconnect, выход и ошибка исполнителя отменяют правила
   и восстанавливают только захваченные назначения. Посторонние изменения других
   клавиш сохраняются. При чужом изменении захваченной клавиши восстановление
   отказывается перезаписывать её вслепую.

Текущий журнал — `recovery/input-ownership.json`, временные SET/readback-снимки —
`recovery/input-sessions/`. Они отделены от истории обычных пользовательских
изменений, чтобы «Восстановить» не возвращало служебное отключённое назначение.
Журнал удаляется только после успешного восстановления. При неизвестном результате
ошибка сохраняется; worker не повторяет SET бесконечно.

У stock-захвата **нет аппаратного срока аренды**: если завершить процесс принудительно
или выдернуть USB, приложение не может мгновенно вернуть клавиши. После подключения
оно читает журнал и предлагает «Восстановить»; обычная запись/новый захват до этого
блокируются. Автоматических SET при первом подключении нет. Полного backup firmware,
калибровки или OS-mode этот журнал не заменяет.

Профиль v2 дополнен `automation.depthChoices`; старый профиль получает пустой список.
Отсутствующий `deepRepeat` мигрирует в `null`, сохраняя прежнее однократное поведение.
Новый выбор с коротким действием предлагает повтор по умолчанию; существующему
правилу его включают явно. В UI — переключатель, три скорости и пауза в подробностях.
Значения сохраняются в общем черновике, профиле, undo/redo и preview применения.
Сохранение, импорт и перезапуск не включают обработчик. Пока окно/его опрос нужны:
при отсутствии heartbeat 5 с правила останавливаются и назначения восстанавливаются.
Самостоятельный фон — отдельный следующий этап.

## Проверки

Core: лёгкий/глубокий цикл, прямой переход к полной глубине, колебания вокруг порога,
независимость слотов, старт с зажатой клавишей, устаревание входа/выхода, конфликтующие
владельцы. Adapter: сохранение остальных байтов/клавиш, повторное восстановление
и отказ при чужом назначении. TS/UI: миграция, ссылки, профиль, undo/redo, preview,
токен запуска, оба языка/темы и размеры окна. Повтор: пауза, гистерезис,
новый цикл, просроченный ввод/очередь, отсутствие догоняющих всплесков, обратная
совместимость профиля и запрет несовместимого действия/варианта ОС.

`verify_depth_choice --run` требует интерактивный терминал. Использует production
KeyboardService/GestureEngine/ActionRuntime, отмечает наш SendInput через
`dwExtraInfo = 0x494f3834`. Диагностический WH_KEYBOARD_LL на отдельном потоке считает
только PageUp/PageDown/VolumeUp/VolumeDown и **всегда** вызывает следующий hook;
он не подавляет ввод. В обычном EXE hook не устанавливается. История печатаемого
текста не собирается. Метод наблюдения:
[Microsoft LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc),
[KBDLLHOOKSTRUCT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-kbdllhookstruct).

Первый production-прогон завершён: лёгкий этап дал 6 PageUp + 16 PageDown и
ноль media; глубокий — 3 VolumeUp + 2 VolumeDown и ноль Page. Down/up сбалансированы,
исходные выбранные события не обнаружены; девять блоков восстановлены.
[Свидетельство и границы](../docs/evidence/exclusive-depth-windows-v1.17.json).
Владелец не наблюдал изменения громкости, поэтому SendInput не считается
подтверждением работы звукового выхода. Повтора в том прогоне не было.

Обновлённый `verify_depth_choice` **подготовлен, собран, но не запускался**:
light → удержание PgDn → отпускание → удержание PgUp → отпускание.
Один интерактивный Enter начинает каждый этап, консоль показывает обратный отсчёт.
Read-only Core Audio измеряет start/end/min/max уровня и mute для default
console/multimedia endpoints; смена endpoint прекращает измерение с восстановлением.
Метод: [GetMasterVolumeLevelScalar](https://learn.microsoft.com/en-us/windows/win32/api/endpointvolume/nf-endpointvolume-iaudioendpointvolume-getmastervolumelevelscalar).
Он проверяет системный регулятор, а не воспроизведение аудио или громкость приложения.
Результат — уникальный `archive_data/session_snapshots/depth-repeat-<timestamp>.json`.
Доступ к Core Audio требуется до захвата; observer не меняет mute или аудионастройки.
Единственные изменения громкости — действия, выбранные по нажатиям владельца.
Не запускать аппаратный тест без готового участника.

Граница результата: принятый захват не доказывает все жесты/макросы и матрицу
objects.md. Реальные результаты Windows-проверки фиксируются отдельно в evidence,
а сценарии crash/unplug/сон/UIPI и конфликт физически удерживаемых модификаторов
остаются отдельной приёмкой. General-purpose leases выходов ещё не реализованы.
