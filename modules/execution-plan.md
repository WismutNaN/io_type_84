# Модуль: план исполнения поведения

Дата: 2026-09-14. **Проект, ещё не код и не новый IPC.** Основание —
[модель объектов](../docs/OBJECT_MODEL.md), [совместимость](../docs/objects/COMPATIBILITY.md)
и [ADR-0009](../docs/adr/0009-behavior-model-and-execution.md).
План сохраняет смысл настройки при выборе DeviceStock / Host / DeviceExtension.

## Ответственность и границы

Profile — намерение пользователя, RawSnapshot — фактическое устройство,
DeploymentPlan — проверенная проекция на исполнителей. Эти объекты не объединяются.
Stock adapter является границей преобразования: `BindingRecord.page`, слоты,
фазовые bytes, marker-коды и лимиты не попадают в универсальный Recognizer.

Планирование не вызывает HID/SendInput, не включает helper и не меняет firmware.
Предполагаемое размещение чистой модели/планировщика: `crates/io-core/src/behavior/`
и `crates/io-core/src/planning/`. Эти каталоги не созданы этим документом.
Существующие codec/changes и service/action_runtime используются через adapters.

## Контракты проектирования

| Контракт | Вход → результат | Инвариант |
|---|---|---|
| validate_profile | Profile + registry → ошибки/нормализованная модель | Ссылки, типы, циклы, budgets; без молчаливой смены семантики |
| resolve_controls | ControlRef + topology + session → SourceBinding | Physical/slot/HID/LED не смешиваются; не угадывать Fn или virtual origin |
| plan_execution | Profile + device/OS evidence + preferences + snapshot → DeploymentPlan | Каждая группа размещена целиком либо имеет точную причину отказа |
| lower_stock | Поддержанный шаблон + RawSnapshot → существующие Edit/ChangePlan | Сохраняет неизвестные байты; не расширяет таблицу вне установленных лимитов |
| build_host_plan | Принятая группа + Input/Output contracts → runtime program | Capture и leases проверяются до запуска, не во время неожиданного KeyDown |
| lower_extension | Поддержанный IR + negotiated API → extension artifact | Своя версия/лимиты; не stock packet с неподтверждённым opcode |
| apply_deployment | Проверенный plan → DeploymentReport | Явные стадии, частичный успех, без заявления общей транзакции USB + ОС |

У результата планирования две независимые оси:

- **Представимость:** exact в известном формате; conditional — кандидат с перечнем
  незакрытых требований; unavailable — нет выбранного пути. Потеря смысла возвращает
  отдельное предложение изменения, не автоматически применённый «приблизительный» план.
- **Доказательства:** schema/codec, write-readback, physical execution, persistence,
  failure recovery. Статус exact не доказывает физическую приёмку.

План содержит binding/behavior IDs, размещение, зависимости helper, InputContract,
OutputContract, пределы задержки/ресурсов, stock diff, опциональный extension artifact,
версию host-графа и диагностические причины. Контракт Input включает качество времени,
порядок, начальное состояние, способ владения исходным вводом и границы устройств.
Контракт Output включает поддержанные target/lifetime, область смешивания и очистку.

## Важнейшее ограничение размещения

Одна конфликтующая группа ввода имеет одного владельца решения. Exclusive tap/deep,
tap/hold с буферизацией, Combo с поглощением и SOCD нельзя разбить между stock и host
после первого вывода обычного символа. Stock может целиком распознать подходящий
шаблон или выдавать принятый поток маркеров, но не одновременно печатать исходный PgUp.

Аналогично все вклады одного управляемого выходного ресурса проходят один output
manager. Контроль только собственных leases не предоставляет контроля чужого
физического ввода. Связанный набор групп может требовать совместного размещения.
Один USB owner не заменяет ни input capture, ни output arbitration.

Пересечение границы разрешено **после принятого решения**: устройство сообщает
событие действия, helper запускает Flow. Для режима host-decision устройство должно
отдать исходный ввод до его обычного HID-эффекта. Обновления прошивки не требуют
перенести LLM/почту/плагины или всю библиотеку Flow на MCU.

## Проверяемые примеры планирования

Это ожидаемые результаты будущего планировщика, не выполненные compiler-тесты.

| Пример | DeviceStock | Host / условие |
|---|---|---|
| Main: A → B, фиксированный RT | Известные binding/RT поля → существующие Edit; физический тест отдельно | Helper не требуется |
| MT: tap Esc / hold Ctrl, 180 мс, без дополнительных interrupt policies | Форма `[9,224,41,18]`; годится только после приёмки именно штатной семантики | Общий TapHold с иными политиками не сворачивать в MT |
| Два независимых уровня DKS, keyboard usages и известные фазы | Кандидат stock-template в пределах 4 actions; сохранить raw | Произвольный macro/consumer action в byte action не помещается семантически |
| Лёгкий PgUp на release / глубокий volume без PgUp | Не объявлять exact по наличию DKS-таблицы | Целый ExclusiveDepth в host, G1/G2 + принятые маркеры или G3; иначе unavailable |
| J+K в окне времени → Esc, без J/K в приложении | CB этого не выражает: он выводит сочетание, а не распознаёт его | Chord + capture; источник наблюдения без захвата даёт `inputOwnershipMissing` |
| Два правила удерживают Shift; физический Shift тоже удерживается | Нет общего stock lease API | Требуется output adapter с доказанным смешиванием; обычный SendInput не даёт допуска |
| If active Photoshop AND variable → Flow(launch, wait, text) | Общего условия/Flow нет | Host + context/process/text adapters, grants и cancellation |
| InvokeControl A → B → A | Не компилировать в последовательность HID | Ошибка цикла; выходной KeyTap не превращать в InvokeControl |
| Telegram unread → мигание T и полосы | Статическая карта не является runtime сценой | Provider + key RGB после G4; полоса требует G5/C. Для единой обязательной сцены отказ, частичная сцена только явно |
| Velocity → gamepad axis | Фиксированным порогом не заменить | G3 + analog target adapter; нет adapter — unavailable, не цифровой WASD |

Потеря части поверхностей/действий не маскируется успехом. Политика optional частей
задаётся самим сценарием; при её отсутствии отказ обязательной ветки блокирует запуск.

## Реальное применение настроек

1. Валидировать профиль/библиотеку, вычислить размещение и показать зависимости.
   Проверить identity, revision, capability evidence и доступность adapters.
2. Сохранить новую версию документа и deployment manifest на ПК. Это ещё не
   активированное поведение и не запись в keyboard flash.
3. Подготовить host runtime, необходимые источники и выходы; не выдавать actions.
   Сохранить исходный snapshot и конкретный stock diff, если он есть.
4. Применить необходимые stock-блоки существующим prepare/apply/readback. До
   завершения не включать зависимое правило. Состояние unknown требует перечитывания.
5. На границе нового цикла ввода активировать согласованную версию runtime.
   Запуск при уже удерживаемой клавише не производит неожиданный tap/deep.
6. Записать отдельно результаты сохранения, device readback и активации runtime.
   Ошибка последнего шага оставляет device snapshot фактическим, правило неактивным
   и доступный restore; общей атомарности здесь нет.

Stock-маркер может оставаться назначенным после аварии helper. Нельзя обещать
автоматический возврат исходного PgUp без принятого механизма: завершённый процесс
не выполнит restore. До применения объяснить поведение без helper и сохранить
путь ручного восстановления. Для автоматического failover может потребоваться
firmware lease. Это часть G1, а не деталь будущего UX.

Смена app context выбирает host-слой в RAM. Она не пишет полный stock-профиль или
порог во flash при каждом переключении окна. Автозапуск/разрешения хранятся локально,
не включаются импортом. Extension admission не включает его функции автоматически.

## Миграция без переписывания устройства

| Этап | Результат и проверка | Откат |
|---|---|---|
| M0 — проверка границ | PgUp/PgDn G1, совместный Shift G2; G3/G4 отдельными сессиями. Сначала спецификация traces, затем выбранный adapter | Stock diff/backup/restore, текущий EXE; firmware не меняется |
| M1 — модель и planner | Новые типы отдельно от codec; ошибки циклов/типов/capabilities, примеры выше и simulator | Новый формат не записывать поверх v2; отключить экспериментальную модель |
| M2 — один сквозной behavior | ExclusiveDepth с pending/commit, OutputLease, отражение в UI/черновике; физическая приёмка | Сохранённые v2 + device snapshot, старый обработчик без новых правил |
| M3 — общий host runtime | Repository, lifecycle/tray, цифровые recognizers/слои/Flow; проверки независимости UI, stop/sleep | Отключить новый autostart, вернуть snapshot/версию профиля, не восстанавливать runtime holds |
| M4 — расширяемые targets | Providers/свет/analog по gates; DeviceExtension только после отдельного допуска | Отключить конкретный adapter и зависимые правила; неизменные авторские definitions |

M0 выполняется до обещания полного stock-пути. M1/M2 разбиваются на небольшие
проверяемые изменения. Текущий `ActionDefinition::Macro` переводится в FlowDefinition,
ActionDefinition — в именованный preset/flow reference; старые ID и варианты ОС
сохраняются. `GestureRule` мигрирует с **additive-семантикой**, а не молча в exclusive.

HardwareSnapshot/BindingRecord/raw остаются transport-моделью. Нельзя полностью
восстановить авторский профиль из таблиц клавиатуры: там нет имён, шаблонов и host
ветвей. Device readback сравнивается с projection manifest; полное редактируемое
намерение хранится на ПК и переносится экспортом профиля.

## Приёмка планировщика и runtime

Нужны проверки содержательных контрактов: отказ split exclusive-группы; сохранение
unknown bytes; матрица exact/conditional/unavailable; отсутствие KeyUp другого lease;
сбой второй стадии применения; stale context под NOT; потеря release/таймера; рекурсия
InvokeControl/CallFlow; повтор/cancel/queue при ограничении ресурсов. Физические
traces сравниваются с намерением отдельно от unit/simulator-тестов.

В M0 фиксировать выбранный backend/версию ОС, приложения и устройства, число
пропущенных/лишних переходов и задержку input-to-output (включая p95/p99). Время
намеренного pending показывать отдельно от транспортной задержки. Успех в обычном
редакторе не распространять без проверки на повышенное окно или иной путь ввода.
Полная совместимость означает принятую область применения, а не обещание для
любой программы. Постоянные журналы нажатий ради этих измерений не включаются.
